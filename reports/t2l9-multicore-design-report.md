# T2L9 设计总结报告

## 一、实验概述

- 任务编号：`T2L9`
- 任务主题：`ch1~ch2 扩展多核的能力`
- 本次实现形成的独立 crate：`joshua912815-rcore-tutorial-t2l9-smp`
- crate 版本：`0.1.0-preview.2`
- crate 交付形态：
  - `cargo run --bin t2l9-ch1-smp`
  - `cargo run` 或 `cargo run --bin t2l9-ch2-smp`

这个实验没有把结果拆成多个 crates.io 包，而是做成了一个可发布的单 crate，原因是 `T2L9` 本身就是一个连续的教学实验：`ch1` 负责建立多核启动直觉，`ch2` 负责在该基础上进一步说明“多核启动不等于多核调度”。用一个 crate 统一承载这两个阶段，更符合助教“一个实验对应一个 crate”的复现方式。

## 二、设计思路与目标

### 1. 适合自己的学习方式

我更适合“工程化拆解 + 现象驱动验证”的学习方式，而不是只看概念定义。具体表现为：

- 先把“能看到的现象”做出来，再反推机制是否理解正确。
- 对每个新增机制都要求有一个明确的可观测结果。
- 优先做最小闭环，而不是一开始就追求完整 SMP 操作系统。

因此，这个实验没有直接追求“ch1~ch2 全面并行调度”，而是先把目标分成两个层次：

1. `ch1`：确认多个 hart 能进入 S-mode、使用独立栈，并打印自己的 hart id。
2. `ch2`：确认多核启动链路可以延续到批处理系统，但只有 boot hart 执行用户程序，secondary harts 进入停车状态。

这种做法更符合我当前阶段的学习节奏：先把启动、角色分工、最小同步关系学明白，再进入更复杂的多核调度与锁设计。

### 2. 初步设想与规划

最初我对 `T2L9` 有三种备选实现路线：

- 路线 A：直接改原有 `tg-rcore-tutorial-ch1` 和 `tg-rcore-tutorial-ch2`
- 路线 B：分别新建两个 crate
- 路线 C：新建一个独立 crate，同时提供 `ch1` 和 `ch2` 两个实验目标

最终选择路线 C，主要原因有三点：

- 更符合“一个实验提交一个 crates.io crate”的约束。
- 可以把 `ch2` 依赖的用户程序源码一并内置，保证复现独立性。
- 可以共享多核启动辅助代码，减少重复实现。

### 3. 关键设计目标

本实验的设计目标分为功能目标和教学目标两类。

功能目标：

- 支持 QEMU `virt` 平台下 `-smp 4` 启动。
- 为每个 hart 分配独立启动栈。
- 在 `ch1` 中让所有 hart 都能进入 S-mode 并输出身份信息。
- 在 `ch2` 中让 boot hart 正常执行批处理程序，其余 hart 停车等待。

教学目标：

- 让学生显式看到 OpenSBI boot hart 选择、SBI HSM 启动 secondary hart、独立栈分配这三件事的关系。
- 让学生理解“系统支持多核启动”与“系统已经支持多核并行调度”是两件不同的事。
- 让学生能通过一个 crate 直接复现实验，而不是依赖课程仓库中的多个路径。

### 4. 核心技术选择

本实验做了三个关键技术选择。

第一，放弃 `-bios none` 路线，改为基于 OpenSBI 的 `-bios default`。

原因是 `T2L9` 的重点是教学性地展示多核启动，而不是自己再实现一层 M-mode 多核启动固件。OpenSBI 已经提供了 HSM 扩展，适合在 S-mode 直接控制 secondary hart 启动。

第二，使用 SBI HSM 扩展而不是假设所有 hart 天然一起进入内核。

这使实验更贴近真实启动流程。boot hart 先进入 S-mode，再显式启动其他 hart，教学含义更清晰。

第三，把 `ch2` 的用户程序源码内置到主 crate 的 `user-src/` 模板目录。

这样做避免了对仓库外路径的依赖，使 `cargo clone CRATE_NAME && cargo run` 可以真正复现整个实验流程。

## 三、实现过程

### 1. crate 结构设计

最终实现的目录结构如下：

```text
tg-rcore-tutorial-t2l9-smp/
├── build.rs
├── src/
│   ├── lib.rs
│   └── bin/
│       ├── t2l9-ch1-smp.rs
│       └── t2l9-ch2-smp.rs
├── user-src/
│   └── src/bin/
│       ├── 00hello_world.rs
│       ├── 08power_3.rs
│       ├── 09power_5.rs
│       └── 10power_7.rs
└── test.sh
```

其中：

- `src/lib.rs` 负责共享 SBI HSM 启动逻辑、boot hart 选择与 console ready 同步。
- `t2l9-ch1-smp.rs` 负责最小多核启动演示。
- `t2l9-ch2-smp.rs` 负责批处理系统的多核扩展演示。
- `user-src/` 保存 `ch2` 用户程序模板源码，主 crate 的 `build.rs` 会在 `OUT_DIR` 中动态生成临时 user crate 并自动编译。

### 2. ch1 的实现要点

`ch1` 的核心改造有三步：

1. 将单启动栈改成“每 hart 独立启动栈”。
2. 使用 OpenSBI 提供的 hart id 作为 `_start` 的输入参数，按 hart id 计算对应栈顶。
3. 由 boot hart 使用 SBI HSM 启动其余 hart，secondary hart 输出信息后进入 `wfi`。

这样做之后，`ch1` 不再只是“Hello, world!” 的最小执行环境，而是多了一个很重要的教学点：**不同 hart 在进入高级语言入口之前，就必须先解决启动栈隔离问题。**

### 3. ch2 的实现要点

`ch2` 的实现思路是“尽量保留原批处理主线，只补多核启动和角色分工”。

具体做法：

- 保留原 `LocalContext` + `AppMeta` + syscall dispatch 的结构。
- 让 boot hart 负责：
  - 清零 BSS
  - 初始化 console
  - 初始化 syscall
  - 逐个装载并运行用户程序
- 让 secondary harts 只负责：
  - 等待 console 初始化完成
  - 输出“secondary hart parked”
  - 进入 `wfi`

这样一来，学生可以很直观看到：

- 多核启动链路已经建立。
- 但任务执行仍然是单核批处理。
- 后续如果要做真正的多核 `ch3~ch5` 调度，需要继续改造调度器、current task 管理和中断处理。

### 4. 验证方式

本实验最终采用 `-smp 4` 作为固定测试环境。

验证结果：

- `ch1`：4 个 hart 都能到达 S-mode，并输出在线状态。
- `ch2`：boot hart 正常运行 4 个用户程序，secondary harts 输出 parked 状态。
- 自动脚本 `./test.sh` 通过。

### 5. 观测指标完成情况

题目要求中明确提出：

- 设计不同的测试环境和例子
- 测试多核执行的特点和优势

为满足这两点，我额外实现了 `observe.sh`，直接在 `-smp 1`、`-smp 2`、`-smp 4` 三种 QEMU 环境下运行两个实验目标。实际观测结果如下：

| 观测环境 | ch1 观测结果 | ch2 观测结果 | 说明 |
|---|---|---|---|
| `-smp 1` | `platform_harts=1`，`all 1 harts reached S-mode` | `detected 1 harts`，`parked=0`，`hello=1`，`power_tests=3` | 证明系统不会错误依赖 secondary hart；单核环境下仍可正常完成批处理 |
| `-smp 2` | `platform_harts=2`，`all 2 harts reached S-mode` | `detected 2 harts`，`parked=1`，`hello=1`，`power_tests=3` | 观察到最小多核角色分化：1 个 boot hart + 1 个 secondary hart |
| `-smp 4` | `platform_harts=4`，`all 4 harts reached S-mode` | `detected 4 harts`，`parked=3`，`hello=1`，`power_tests=3` | 观察到完整多核启动链路，但批处理执行仍保持单核 |

这些结果说明本实验已经覆盖了“不同测试环境”的要求，也能支持学生比较多核启动能力在不同 `-smp` 配置下的表现。

### 6. 多核特点与优势分析

通过上述观测结果，可以总结出三点多核特点与优势。

第一，`ch1` 中的优势是“多核启动能力可见化”。

原始 `ch1` 只能说明一个 hart 能否进入 S-mode；扩展后，学生可以直接看到不同数量的 hart 都能正确启动并分配独立栈。这让“多核启动”不再只是概念，而是可以通过日志直接验证的事实。

第二，`ch2` 中的优势是“多核启动与单核执行的边界被明确区分”。

在 `-smp 2` 和 `-smp 4` 环境下，secondary hart 都能被正确启动并停车，而 boot hart 独占批处理执行。这说明系统已经具备多核 bring-up 能力，但还没有进入真正的多核调度阶段。这个边界对教学非常关键。

第三，不同 `-smp` 环境下的输出差异本身就是多核编程现象。

在更高并发下，共享串口输出会更容易产生交错和竞争。为了让观测指标稳定，我在 `ch1/ch2` 的 console 实现里额外加了最小串口锁。这也让学生看到：即使只是“打印日志”，在多核里也会立刻变成同步问题。

## 四、与 AI 合作的实现过程

### 1. AI 的使用方式

我这次没有把 AI 当成“自动写完整代码的黑盒”，而是把它当成三个角色来使用：

- 代码库检索器：帮助快速定位 `ch1/ch2`、`tg-linker`、`tg-sbi`、`tg-syscall` 的关键实现位置。
- 方案比较器：先评估 `9~17` 哪些任务更适合当前仓库，再收敛到 `T2L9`。
- 实现协作者：在我给出“单 crate 提交”的约束后，重新调整结构设计并完成实现。

### 2. 关键交互与修正过程

本次与 AI 协作中有三个典型问题。

#### 问题一：一开始把结果拆成了两个 crate

最开始，AI 想按 `ch1-smp` 和 `ch2-smp` 分别做两个独立 crate。这在工程上是合理的，但不符合“最后只提交一个 crates.io crate”的要求。

修正方式：

- 我及时指出约束。
- AI 随即把方案改成“一个主 crate + 两个 bin + 一个内置 user 子工程”。

这个过程说明：AI 很擅长给出结构清晰的工程方案，但**约束条件仍然需要由人明确兜底**。

#### 问题二：错误地假设 boot hart 一定是 hart 0

这是本次实现中最关键的真实 bug。

最初代码写成了“`hart_id == 0` 就是 boot hart”。但在实际运行 `ch2` 时，OpenSBI 一次启动里把 `hart 1` 选成了 boot hart，导致：

- 真正的 boot hart被误判成 secondary hart
- 它在等待 console ready
- `hart 0` 根本没有被启动
- 系统卡住

修正方式：

- 引入一个 `BOOT_HART` 原子变量。
- 让第一个进入内核的 hart 通过 `compare_exchange` 抢占 boot 角色。
- 其余 hart 自动视为 secondary hart。

这个 bug 非常有教学价值，因为它直接暴露了一个常见误区：**很多“看起来天然成立”的多核假设，其实只是单核思维的延伸。**

#### 问题三：如何保证 crate 独立可复现

原始 `ch2` 的 build 流程依赖课程仓库中的 `tg-rcore-tutorial-user`。如果直接照搬，发布到 crates.io 后很难独立复现。

修正方式：

- 将 `ch2` 需要的最小用户程序子集放进当前 crate 的 `user-src/` 模板目录。
- 主 crate 的 `build.rs` 在构建时自动编译这些用户程序，并生成 `APP_ASM`。

这样就把“仓库内路径依赖”改造成了“包内源码依赖”，满足了独立性要求。

#### 问题四：并发串口输出交错导致观测结果不稳定

在补做观测指标时，我一开始直接统计日志中的 `hart online` 和 `secondary hart` 文本出现次数。结果发现 `-smp 2/4` 环境下输出会被多个 hart 交错写入，导致统计不稳定。

修正方式：

- 给 `ch1/ch2` 的 console 实现加了最小串口锁。
- 让 `observe.sh` 统计更稳定的模式，例如 `platform_harts`、`parked` 和 `power_tests`。

这个问题再次说明：多核里最先暴露出来的 bug 往往不是调度，而是共享资源访问。

### 3. 对 AI 协作效果的评价

我对这次 AI 协作效果的评价是：

- 在代码库阅读和方案收敛上，提升明显。
- 在工程化落地上，效率较高。
- 在约束一致性和真实硬件语义上，仍然需要人工审题和验收。

具体来说，AI 适合做：

- 快速比较方案难度。
- 批量生成新 crate 的模板、文档、测试脚本。
- 在发现 bug 后快速重构结构。

但 AI 不适合单独负责：

- 判断题目隐含约束是否被满足。
- 默认相信某些平台行为，例如“boot hart 就是 0”。
- 代替真实运行验证。

## 五、学习效果评估

### 1. 知识与能力提升

通过这次实验，我觉得自己在三个方面的提升最明显。

第一，对 RISC-V 多核启动链路的理解更具体了。

以前我知道“多核 = 多个 hart”，但理解偏概念化。现在我更清楚：

- boot hart 是平台或固件选出来的，不一定固定为 0。
- secondary hart 通常不是自动开始执行内核，而是需要显式启动。
- 独立启动栈是多核内核最早必须解决的问题之一。

第二，对“教学内核扩展边界”的判断更清楚了。

这次实现让我明确区分了三件事：

- 支持多核启动
- 支持多核进入内核
- 支持多核并行调度和共享内核数据结构

以前我会把它们笼统地看成“做 SMP”。现在我知道，这其实是不同阶段的问题。

第三，对“做成可提交实验 crate”这件事有了更强的工程意识。

以前写课程实验容易默认依赖整个仓库。现在我会主动考虑：

- 能不能单包复现
- 构建脚本有没有外部路径依赖
- README 是否足够支撑助教复现

### 2. 能力上可能的下降或代价

这次与 AI 深度协作也有一个代价：我在“从零手写所有样板代码”的比例上有所下降。

例如：

- crate 脚手架
- README 初稿
- 测试脚本骨架
- 一些重复性的 manifest 改写

这些部分我更多依赖了 AI。短期看这确实提高了效率，但如果完全不审查，也可能削弱我自己维护工程细节的能力。

所以我的调整策略是：

- 让 AI 先做结构化初稿
- 自己重点审查启动路径、同步关系、平台假设和最终运行结果

这样既保留效率，也不放弃关键能力训练。

### 3. 与现有教学实验教程的定量/定性比较

#### 定量比较

以原始 `ch1/ch2` 和本实验对比，可以得到一个简单量化结果。

| 对比项 | 原始 ch1/ch2 | T2L9 实验版本 |
|---|---|---|
| QEMU hart 数 | 1 | 4 |
| 可观测 hart 身份 | 否 | 是 |
| secondary hart 启动路径 | 无 | 有 |
| 明确展示 boot/secondary 角色分工 | 否 | 是 |
| 单 crate 复现 | 否 | 是 |
| 自动测试脚本 | 原章节各自独立 | 一个脚本覆盖两个阶段 |

#### 定性比较

原始教程的优点是主线很干净，适合第一次理解单核内核执行环境和批处理系统。

本实验版本的优点是：

- 更贴近“真实硬件不会默认只有一个核”这一事实。
- 更适合把“多核启动”作为单独知识点讲清楚。
- 更容易引出后续 `ch3~ch5` 多核任务管理的设计难点。

但它也有明显代价：

- 启动流程复杂度上升。
- OpenSBI 和 HSM 会给初学者增加一层背景知识。
- 输出中存在多 hart 并发打印导致的交错，需要额外解释。

因此我认为，这个实验**不适合替代原始 `ch1/ch2` 主线**，更适合作为：

- 原主线之外的个性化扩展实验
- 面向已经完成基础章节同学的进阶模块

## 六、总结

这次 `T2L9` 的核心成果不是“做出了一个完整 SMP OS”，而是把“多核启动”这件事从抽象概念变成了一个可复现、可观察、可提交的教学实验 crate。

我认为这个实验最有价值的地方有三点：

- 它把“多核支持”的最小边界讲清楚了。
- 它暴露了真实的平台语义问题，例如 boot hart 不固定为 0。
- 它通过单 crate 封装，把实验的独立性和可复现性提升到了更高水平。

如果继续往下扩展，我下一步会优先考虑：

1. 给 `ch3~ch5` 做真正的 per-hart current task 管理。
2. 引入多核下的自旋锁或关中断保护。
3. 设计“多核启动成功但调度仍是单核”的对照实验，再逐步演进到真正的并行调度。
