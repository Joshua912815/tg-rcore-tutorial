# `ch8-doom` 游戏实验独立总结报告

## 1. 实验背景与任务理解

本实验对应 `tg-rcore-tutorial` 根目录 `README.md` 中给出的 `ch8-doom` 要求：

> 移植用户态跨平台版 Doom 游戏，通过 Framebuffer 实现 3D 软件渲染；在 ch8 基础上扩展内核功能，支持运行用户态跨平台版 Doom 游戏。

我对这个要求的理解是：

1. 这不是重新设计一个简化版射击游戏，而是要在 `ch8` 现有内核基础上，真正移植一个已有的用户态 Doom 程序。
2. 实验重点不是“把游戏贴到仓库里”，而是打通一条完整的运行链路：
   - `ch8` 内核初始化图形设备
   - 提供 framebuffer 呈现能力
   - 提供最基本的输入、文件、堆扩展等用户态运行支持
   - 将 `doomgeneric` 作为用户程序编译、打包、装入文件系统镜像
   - 在 QEMU 中实际进入 Doom 标题界面并能进入游戏
3. `ch8` 本身原本重点是线程与同步原语，但本实验要求在此之上进一步扩展成“能够承载较大型用户态图形程序”的内核，因此本实验本质上是一次跨层集成工作，而不是只补某一个系统调用。

因此，我给自己设定的实验目标不是“做一个看起来像 Doom 的 demo”，而是：

> 在不破坏 `ch8` 原有教学主线的前提下，将 `doomgeneric` 作为用户态程序移植到 `tg-rcore-tutorial-ch8`，让它能够通过 framebuffer 在 QEMU 中完成图形渲染，并能实际进入游戏。

## 2. 实验目标

本次 `ch8-doom` 独立实验的具体目标如下：

1. 从 `ch8` 基线切出独立分支，避免与其他实验相互干扰。
2. 在 `ch8` 中加入 VirtIO-GPU / framebuffer 支持，使内核具备图形显示能力。
3. 为用户态程序补充 Doom 运行所必须的系统能力，包括图形呈现、输入轮询、`lseek`、`sbrk` 等。
4. 将上游 `doomgeneric` 移植到当前仓库，完成适配层、启动代码、链接脚本与构建流程。
5. 将 `doom1.wad` 打包进入 `fs.img`，让 Doom 在 QEMU 中可直接找到资源文件。
6. 让 `initproc` 开机后直接进入 Doom，降低验证门槛。
7. 完成本地验证，确保能够看到标题界面、进入实际游戏画面，并进行基本控制。
8. 形成一份独立实验报告，清晰说明实现内容、AI 协作过程、问题修复过程与学习效果。

## 4. 我实际完成了哪些工作

这一部分是本报告最核心的内容，用来明确回答“我到底做了什么”。

### 4.1 扩展了 `ch8` 的运行方式

原始 `ch8` 的运行方式主要围绕串口和块设备，默认不承担图形应用的展示需求。

为了支持 Doom 图形输出，我修改了 `tg-rcore-tutorial-ch8/.cargo/config.toml`，使运行方式具备：

1. 本地 QEMU 图形窗口显示能力
2. 串口日志保留在终端，方便调试
3. `virtio-mmio-bus.0` 上挂载块设备镜像
4. `virtio-mmio-bus.1` 上挂载 VirtIO-GPU 设备

修改后，`cargo run` 不再只是“字符界面内核启动”，而是可以真正展示 Doom 渲染出来的图像。

### 4.2 为 `ch8` 引入了 VirtIO-GPU / Framebuffer 支持

原始 `ch8` 重点在并发与同步，没有现成的图形子系统。

我在 `tg-rcore-tutorial-ch8/src/virtio_gpu.rs` 中新增了 GPU 封装模块，并在 `tg-rcore-tutorial-ch8/src/main.rs` 中完成：

1. GPU MMIO 区间登记
2. VirtIO-GPU 初始化
3. 分辨率读取
4. framebuffer 信息导出
5. framebuffer 刷新呈现

这一部分的核心意义在于：

- 内核第一次具备了稳定的像素级输出能力
- 用户态程序不需要直接操作设备，只需通过系统调用提交一块 RGBA 图像缓冲区
- 内核负责把用户态缓冲区复制出来，再居中绘制到 QEMU 的实际 framebuffer 上

实际运行中，Doom 逻辑分辨率为 `320x200`，经自动放大后形成 `640x400` 图像，再居中显示在更大的屏幕分辨率中。

### 4.3 为用户态程序补充了 Doom 运行所需的系统能力

移植 Doom 不是单纯把可执行文件放进镜像即可。`doomgeneric` 运行过程中需要比一般小测例更多的运行时支持。

我在 `tg-rcore-tutorial-syscall` 和 `tg-rcore-tutorial-ch8/src/main.rs` 中补充了以下能力：

1. `framebuffer_info`
2. `framebuffer_present`
3. `input_poll`
4. `lseek`
5. `sbrk`

这些能力分别解决了下面的问题：

- `framebuffer_info` / `framebuffer_present`：让 Doom 能把每一帧软件渲染结果交给内核显示
- `input_poll`：让 Doom 从当前实现的输入源轮询按键
- `lseek`：让 WAD 文件按偏移读取资源块
- `sbrk`：让 picolibc / Doom 的运行时堆空间能够扩展

如果缺少其中任何一个环节，Doom 都会在初始化阶段提前失败，或者即使启动也无法正常加载资源与刷新画面。

### 4.4 移植并适配了 `doomgeneric`

本实验没有自己重写 Doom，而是按任务要求移植了上游 `doomgeneric`。

我在 `tg-rcore-tutorial-ch8/vendor/doomgeneric` 中放入上游源码，并新增了以下 Doom 侧适配文件：

- `tg-rcore-tutorial-ch8/doom/doomgeneric_tg.c`
- `tg-rcore-tutorial-ch8/doom/tg_picolibc.c`
- `tg-rcore-tutorial-ch8/doom/start.c`
- `tg-rcore-tutorial-ch8/doom/link.ld`

其中最关键的是 `doomgeneric_tg.c`，它负责把 DoomGeneric 所需的平台接口映射到当前内核提供的能力上，包括：

1. 将每帧 `DG_ScreenBuffer` 提交给 `framebuffer_present`
2. 轮询 `input_poll` 获取按键
3. 把终端输入映射为 Doom 的 `KEY_UPARROW / KEY_DOWNARROW / KEY_FIRE / KEY_USE` 等键值
4. 选择优先加载 `doom1.wad`

这一层可以理解为：

> 把一个“跨平台用户态 Doom 框架”适配成“可以跑在 tg-rcore-tutorial-ch8 上的 Doom 用户程序”。

### 4.5 为 Doom 构建链补齐了文件与资源打包流程

除了内核与适配层，还必须解决“怎么把 Doom 编出来并带进镜像”的问题。

我修改了 `tg-rcore-tutorial-ch8/build.rs`，主要完成了以下工作：

1. 在构建阶段编译 Doom 用户程序
2. 将 Doom 可执行文件打包进 `fs.img`
3. 将 `doom1.wad` 打包进 `fs.img`
4. 扩大文件系统镜像容量，避免资源文件过大导致空间不足
5. 让 `initproc` 在本分支中自动执行 `doom`

这意味着本实验最终不是“手动上传一个外部文件再试运行”，而是做到了：

- `cargo run`
- 自动构建内核
- 自动构建 Doom
- 自动打包资源
- 自动启动 Doom

整个流程具有较好的可复现性。

### 4.6 修复了 Doom 初始化阶段的多个关键问题

这次实验真正的难点不是“把标题界面画出来”，而是把 Doom 从一连串早期错误里拉到可运行状态。

我实际解决的关键问题包括：

1. `StorePageFault`
2. `errno` / TLS 写空指针问题
3. `fseek/ftell` 相关 stdio 路径不稳定
4. WAD 资源文件版本不匹配
5. 输入事件“按下立刻弹起”，导致 `WASD` 不能驱动人物移动

对应的修复策略是：

1. 在 `tg_picolibc.c` 中去掉依赖 TLS `errno` 的显式写法，避免 bare-metal 场景下访问空地址
2. 在 `vendor/doomgeneric/w_file_stdc.c` 中改用 `open/lseek/read/close` 直接读取 WAD，绕开不稳定的 `FILE*` 路径
3. 将资源包切换到 `doom1.wad` shareware v1.9，解决 `STBAR not found!` 等资源缺失问题
4. 在 `doomgeneric_tg.c` 中把输入模型改为“短按保持一段时间再自动释放”，让 `WASD` 这种移动键真正生效

这些问题中，很多都不是普通的语法错误，而是“用户态 C 运行时、资源文件格式、内核系统调用能力”三者交叉产生的兼容性问题。

### 4.7 当前版本的输入模型是“终端输入 + QEMU 图形显示”

需要诚实说明的一点是：当前版本图像显示在 QEMU 图形窗口中，但输入仍然来自运行 `cargo run` 的终端，而不是直接从 QEMU 图形窗口读取键盘。

当前可用控制方式为：

- `w`：前进 / 菜单上
- `s`：后退 / 菜单下
- `a`：左转
- `d`：右转
- `space` / `f`：开火
- `e`：开门 / 使用
- `q` 或 `Esc`：菜单
- `Enter`：确认

虽然这不如“图形窗口直接接收键盘”那样自然，但它已经满足了本实验对 Doom 运行和基本交互的要求。

### 4.8 同步更新了启动与用户程序打包逻辑

为了让老师或同学验证更方便，我还修改了：

- `tg-rcore-tutorial-user/src/bin/initproc.rs`

让当前分支下系统启动后直接进入 Doom，而不是先进 shell 再手动敲命令。

这样做的优点是：

1. 验证路径更短
2. 更接近“开机即进入游戏”的最终效果
3. 便于截图和演示

## 5. 关键实现思路

### 5.1 为什么 `ch8` 适合做 Doom

我认为 Doom 这种用户态图形应用不适合放在低章节完成，而 `ch8` 比较适合，原因如下：

1. `ch8` 已经具备相对完整的用户态程序运行框架
2. 有文件系统，能够容纳和读取 WAD 资源文件
3. 有线程与同步原语基础，内核结构比前几章更成熟
4. 更容易扩展新的系统调用而不破坏整体框架

换句话说，Doom 并不是一个“图形更炫的 snake”，它对运行时环境的要求明显更高，因此放在 `ch8` 更合理。

### 5.2 为什么采用 “移植现有 Doom” 而不是自己重写一版简化 3D 游戏

本次任务原始要求已经明确给出了 `doomgeneric` 作为推荐方案。

我选择移植现有 `doomgeneric` 的原因是：

1. 这更符合实验原意，即“移植用户态跨平台版 Doom”
2. 可以把精力集中在操作系统接口适配，而不是游戏逻辑重写
3. 现有代码规模更大，更能体现内核支持能力是否真实够用
4. 移植成功后展示效果更直观，也更有说服力

因此，本实验的真正价值在于：

> 证明 `tg-rcore-tutorial-ch8` 已经可以承载一个真实的、非玩具级的用户态图形程序。

### 5.3 为什么 framebuffer 呈现应放在 syscall 层，而不是让用户态直接操作 GPU

我没有让 Doom 直接访问 MMIO 设备，而是通过系统调用把帧缓冲区交给内核显示。原因是：

1. 这更符合内核/用户态权限边界
2. 用户态只需关心“我要显示一帧图像”，不需要关心设备细节
3. 内核可以统一做用户态内存校验和缓冲区复制
4. 更方便在后续扩展到其他图形应用

这一设计也让 DoomGeneric 的平台适配层更清晰：它只面对少量稳定接口，而不是直接依赖设备寄存器。

### 5.4 为什么需要补 `lseek` 与 `sbrk`

一开始很容易把 Doom 移植理解为“只要有画图和键盘就够了”，但实际不是这样。

Doom 至少还依赖：

1. 顺序和随机读取 WAD 资源文件
2. 运行时堆内存扩展

所以 `lseek` 与 `sbrk` 并不是附带优化，而是基本生存条件。这个认识让我更加清楚地看到：

> 较大型用户态程序能否运行，往往取决于一组看起来“不显眼”的基础系统能力是否齐全。

## 6. 与 AI 合作的实现过程

这是本实验报告的重要部分，因为原始要求明确提出要总结与 AI 合作的过程。

### 6.1 我如何与 AI 交互

本次实验中，我没有把 AI 当成“直接把 Doom 搬进来”的黑盒工具，而是把它当成三个角色来使用：

1. 代码库分析助手
2. 移植方案讨论助手
3. 调试与收敛助手

具体过程如下。

#### 第一阶段：先让 AI 读任务要求和 `README`

我先要求 AI：

- 阅读根目录 `README.md` 中关于 `ch8-doom` 的描述
- 结合 `tg-rcore-tutorial-ch8/README.md` 理解任务边界
- 明确本实验不是新写一个小游戏，而是移植 `doomgeneric`

这一步的价值在于先统一方向，避免把时间花在“自己写一套简化 3D 引擎”这种偏离任务的实现上。

#### 第二阶段：让 AI 先看仓库代码，再判断应该补哪些能力

我没有一开始就要求 AI 直接写 Doom 适配层，而是先让它：

- 检查 `ch8` 当前有没有 GPU 支持
- 检查 syscall 层哪些能力缺失
- 判断 Doom 运行最低需要哪些接口

通过这一步，AI 很快把问题拆解成：

1. 图形呈现
2. 输入轮询
3. WAD 文件读取
4. 堆扩展
5. 构建与打包链路

这让我从“移植 Doom 好像很大很杂”切换到了“先补五类必需能力”的可执行路径。

#### 第三阶段：分块推进实现，而不是一次性全改

在实现过程中，我让 AI 按模块推进：

1. 先建分支
2. 再补 GPU / syscall
3. 再接 DoomGeneric 适配层
4. 再接 build.rs 与资源打包
5. 最后运行、定位错误、收敛输入

这种方式相比“一次性改很多文件再整体编译”更可控，也更方便逐步定位问题。

### 6.2 AI 帮助我定位和解决的问题

本次实验中，AI 对我帮助最大的不是“重写 Doom 本身”，而是帮助我迅速定位真正阻塞移植成功的关键点。

主要包括以下几个问题。

#### 问题一：最开始对 Doom 任务的理解容易过于简单

最初直觉上会觉得：

- “这应该主要就是复现一个现有游戏”

这个方向本身没错，但如果只停留在这个表述上，会忽略下面这些关键事实：

- `doomgeneric` 不是简单单文件程序
- Doom 需要 WAD 文件
- 需要稳定的文件随机访问能力
- 需要堆扩展
- 需要每帧刷新图形
- 需要可用输入模型

AI 帮我把这个任务明确拆成“内核扩展 + 用户态适配 + 资源打包 + 输入调试”四条主线。

#### 问题二：Doom 早期崩溃并不是单一 bug

第一次启动 Doom 时，系统在初始化早期出现 `StorePageFault`。如果没有足够经验，很容易把它粗暴理解为“页表没映射好”。

AI 通过继续读日志、回看 C 运行时路径，帮助我逐步确认：

1. 一部分 fault 来自 `errno` / TLS 写入空地址
2. 一部分问题来自 stdio 路径里的 `fseek/ftell`
3. 单纯扩大地址空间并不能解决根因

最后的修复不是“再映射几页内存”，而是改写 picolibc / Doom 文件读取路径。

#### 问题三：WAD 文件不是“随便一个 Doom1.wad 都行”

中途还遇到过：

```text
STBAR not found!
```

AI 没有把这个问题误判成绘图 bug，而是帮助我把注意力转向资源包版本匹配。

最终确认：

- 早期拿到的 WAD 版本不对
- 需要换成 Doom Shareware v1.9 对应资源

这让我认识到，游戏移植里“资源格式和版本”与“代码逻辑”一样关键。

#### 问题四：标题界面能显示，不等于真正可玩

后期当 Doom 标题界面已经能显示时，一开始看上去像是任务已经基本完成。但用户验证时发现：

- `q` 键有反应
- `WASD` 却不能驱动人物移动

AI 继续回看 `doomgeneric_tg.c` 输入模型后判断出原因：

- 之前的实现把按键写成“按下立即释放”
- 菜单类按键还能凑合用
- 需要持续一小段时间的移动键等于没有被按住

随后补上了“短按保持再自动释放”的输入策略，问题才真正解决。

### 6.3 与 AI 合作中的一个重要体会

我觉得这次和 AI 协作最有效的一点是：

> 不让 AI 直接“把 Doom 搬进来”，而是让它持续帮助我缩小问题空间。

比如在不同阶段，AI 分别承担了不同角色：

1. 任务边界澄清者
2. 构建链路整理者
3. 运行时崩溃归因者
4. 输入行为调优者
5. 文档整理者

这种协作方式比“一开始就让 AI 生成一大堆代码”更稳，也更有利于我自己理解问题。

## 7. 实际遇到的问题、Bug 与解决过程

### 7.1 仅有图形 syscall 还不够

#### 现象

最初很容易认为 Doom 只需要：

1. 画图
2. 键盘

#### 分析

但真实情况是 Doom 初始化还依赖：

- WAD 文件随机读取
- 运行时堆扩展
- 相对完整的 C 运行时适配

#### 解决

补充 `lseek`、`sbrk`，并为 picolibc 提供最小可用的 syscall 支撑。

### 7.2 页错误并不一定是页表问题

#### 现象

首次启动 Doom 时在 `Z_Init` 之后出现 `StorePageFault`。

#### 分析

继续沿调用链排查后发现，问题并不只是“内存页没映射”，而是 C 运行时里的 `errno` / TLS 假设不成立，导致写空地址。

#### 解决

在 `tg_picolibc.c` 中改成更适合当前 bare-metal 用户态环境的处理方式，避免对不可靠 TLS 路径的依赖。

### 7.3 stdio 文件路径不稳定

#### 现象

继续运行后，Doom 在读取 WAD 过程中仍然异常。

#### 分析

`FILE*` + `fseek/fread` 这一路在当前环境里不稳定，不适合继续依赖。

#### 解决

将 `w_file_stdc.c` 改成更直接的：

- `open`
- `lseek`
- `read`
- `close`

这样让资源读取路径更贴近当前内核已经实现好的 syscall 集合。

### 7.4 资源包版本不匹配

#### 现象

出现 `STBAR not found!`，标题资源缺失。

#### 分析

问题不在图形呈现，而在于 WAD 文件版本不对。

#### 解决

更换为 `doom1.wad` shareware v1.9，并在构建阶段优先打包该资源。

### 7.5 标题界面可见，但 `WASD` 不能移动

#### 现象

玩家已经可以进入游戏画面，但 `WASD` 无法控制人物。

#### 分析

输入模型先前是“按下马上释放”，这对菜单键尚可，对持续动作不够。

#### 解决

在 `doomgeneric_tg.c` 中引入活动键表和短按保持时间，使移动键能维持一小段时间后再自动释放。

### 7.6 QEMU 图形窗口与终端输入职责分离

#### 现象

用户在 QEMU 图形窗口里按键时感觉“游戏没有反应”。

#### 分析

当前实现是：

- QEMU 窗口负责显示
- 终端负责输入

这不是程序卡死，而是输入源设计如此。

#### 解决

明确说明当前交互方式，并在适配层中保持稳定的终端输入映射。虽然仍有交互体验上的改进空间，但不影响实验目标完成。

### 9.1 知识方面的提升

本实验让我在以下几个方面有了明显提升。

#### 9.1.1 对“用户态大程序依赖什么内核能力”的理解更具体了

以前做前几章实验时，更多是在补小型 syscall 或通过测例。做完 `ch8-doom` 后，我更直观地理解了：

- 一个真实用户程序不仅需要 `read/write`
- 还需要堆扩展、文件偏移、资源读取、图形输出、输入获取等一整套配套能力

这让我对“操作系统为应用提供的运行时支撑”有了更系统的认识。

#### 9.1.2 对 framebuffer 软件渲染链路的理解更具体了

通过 Doom 适配，我更具体地理解了：

1. 软件渲染结果如何形成一块像素缓冲区
2. 这块缓冲区如何通过 syscall 提交给内核
3. 内核如何把用户态缓冲区复制并显示到真实 framebuffer
4. 为什么分辨率、缩放与居中策略会影响最终显示效果

这比只看教程中的“静态图片显示”更进一步。

#### 9.1.3 对 C 运行时与内核边界的理解更深了

本次移植里最有价值的一点，是我第一次比较明确地体会到：

- 用户态 C 程序默认依赖很多运行时假设
- bare-metal 环境不一定满足这些假设
- `errno`、`FILE*`、`fseek` 这些看似普通的接口，到了最小 OS 环境里都可能成为真实 bug 来源

这让我比以前更能理解“移植大型程序”为什么总会牵扯运行时兼容问题。

### 9.2 能力方面的提升

#### 9.2.1 工程拆解能力提升

最初看到 “ch8-doom” 时，直觉会觉得这只是“把 Doom 搬过来”。真正做下来以后，我发现至少要拆成：

1. 图形设备支持
2. syscall 扩展
3. 用户态适配层
4. 文件系统镜像打包
5. 资源版本匹配
6. 输入行为调试

这次实验让我更意识到，操作系统项目里的大任务必须拆成多个跨层小问题才能落地。

#### 9.2.2 调试能力提升

这次实验里我实际练习了：

- 根据内核 trap 日志判断故障阶段
- 根据 Doom 初始化日志推断失败位置
- 将 C 运行时问题与内核 syscall 能力缺口区分开
- 用“标题界面出现了”和“真正可玩了”这两个不同标准去验收程序

这比单纯通过 checker 的实验更接近真实系统移植工作。

#### 9.2.3 与 AI 协作的能力提升

以前我更容易把 AI 当成问答工具，这次更像在练习“如何管理一个协作式系统移植助手”。

1. 先让 AI 缩小问题空间
2. 再让 AI 聚焦当前唯一的阻塞点

4. 验证失败时，把现象、日志和上下文一起交给 AI，而不是只贴一段代码

这种方式比一次性让 AI 生成大量代码更稳。

- 只有在“自己持续参与判断与验收”的前提下，AI 才会真正带来能力增长

### 9.4 与本校现有教学实验教程的对比

#### 9.4.1 定性对比

与原始 `ch8` 教程相比，本实验的主要变化是：

1. 原始 `ch8` 更强调线程、同步原语、阻塞与唤醒

原始教程的优点是：

- 主题集中
- 更适合讲清并发基础概念
- 更容易通过小测例验证

本实验扩展版的优点是：

- 更贴近真实应用移植
- 更能体现系统调用、文件系统、图形设备、运行时适配之间的联动

- 对后续更复杂的 OS 应用实验有明显启发

如果做一个粗略但直观的量化比较，我会这样评价：

| 对比项 | 原始 `ch8` | `ch8-doom` 扩展版 |
|---|---|---|
| 主要验证对象 | 线程/同步测例 | 真实用户态图形程序 |
| 新增系统能力类型 | 较少 | framebuffer、输入、`lseek`、`sbrk`、构建打包 |

| 调试难度 | 中等 | 高 |
| 图形化展示效果 | 无 | 有 |
| 综合性 | 中等 | 很高 |

我的主观评价是：

- 如果目标是“讲清并发概念”，原始 `ch8` 更聚焦
- 如果目标是“检验内核能否支撑复杂应用”，`ch8-doom` 更有挑战性也更有训练价值
