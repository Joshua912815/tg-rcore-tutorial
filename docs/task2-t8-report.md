# T8 设计总结报告：面向 tg-rcore-tutorial 的工程质量型个性化实验改造

## 一、选题背景与个性化定位

我选择 `TASK2.md` 中的 T8“完善现有实验（工程质量方向的个性化改造）”作为本次个性化实验设计的第一项任务。原因很直接：`tg-rcore-tutorial` 目前已经具备较完整的章节化教学主线，覆盖了启动、Trap、系统调用、调度、虚存、进程、文件系统、信号与同步等核心内容，但在“工程化学习体验”方面仍有明显改进空间。具体表现为：

- 不同章节的可观测性能力分散在各处，缺少统一的 tracing/metrics 入口；
- 测试虽然已经具备基础脚本和 checker，但偏重“能否通过”，缺少“为什么失败、失败后如何定位”的支撑；
- 调试经验主要隐含在源码和 README 中，缺少结构化的“常见 bug 清单 + 定位手册”；
- 文档风格整体较完善，但不同章节在“目标、关键代码点、测试指标、思考题”的组织粒度上仍可进一步统一。

对我来说，这个方向比直接添加一个全新的大功能更适合作为个性化实验教程的切入点。我的学习方式更偏向工程化和数据驱动：

- 我希望先搭好观测和验证框架，再深入理解机制本身；
- 我更容易通过“现象 - 指标 - 代码路径”三者闭环建立系统认识；
- 我倾向于把每个实验做成“可以复现、可以对比、可以排错”的小型工程，而不只是一次性完成作业。

因此，本次个性化改造的核心定位是：

**把现有教程从“能运行的教学内核”提升为“可观测、可验证、可调试、可维护的教学实验系统”。**

这一定义与 `TASK2.md` 中“把课程内容变成可验证的内核机制”的思路一致，但我选择的切入角度不是新增课程点，而是提升整个教程的工程质量与学习效率。

## 二、设计思路与目标

### 2.1 总体目标

本次 T8 的总体目标不是推翻现有教程，而是在尽量保留其章节结构和教学主线的前提下，做四类增强：

1. 统一 tracing/metrics 框架；
2. 补强测试体系；
3. 提升调试体验；
4. 重构教程文档模板。

这四类增强共同服务于一个更具体的教学目标：

**让每个章节都具备“目标明确、关键路径清楚、异常可定位、结果可验证、行为可比较”的学习闭环。**

### 2.2 与当前仓库结构的结合

这个改造方案不是抽象设计，而是明确绑定当前仓库已有的模块和工作流。

现有仓库中已经具备几个非常适合作为改造支点的基础设施：

- `tg-rcore-tutorial-console` 已经提供统一的 `print!`/`println!`/`log` 输出路径，可作为 tracing 的底层输出接口；
- `tg-rcore-tutorial-checker` 已经具备基于正则模式的输出校验能力，可作为回归测试框架的基础；
- 各章节已有 `test.sh` 脚本，可作为脚本化回归入口；
- `ch3` 已经实现了最小的 `trace` 能力和 syscall 计数，说明“可观测性”在仓库中已有雏形；
- `ch8` 已经包含同步、阻塞、死锁检测等更复杂场景，适合作为 lock contention 和线程状态观测的实验样本。

因此，本次改造并不追求另起炉灶，而是把已有分散能力收束为一致的工程规范。

### 2.3 四个具体改造模块

#### 模块 A：统一 tracing / metrics 框架

当前教程中的日志能力已经存在，但缺少统一事件模型。我的设计目标是将“系统调用、异常、调度、缺页、锁竞争”统一到一套事件接口中。

我计划将 tracing 统一抽象为如下逻辑结构：

- 事件类别：`syscall` / `trap` / `schedule` / `vm` / `sync`
- 所属章节：`ch3`、`ch4`、`ch5`、`ch8` 等
- 事件来源：进程 ID、线程 ID、任务 ID
- 时间信息：逻辑时间戳或 tick
- 事件载荷：如 syscall ID、trap 类型、页错误地址、锁 ID、等待时长

在输出层上，分为两种形式：

- 面向学生直接阅读的人类可读日志；
- 面向实验报告统计的结构化指标摘要。

这个设计与当前仓库高度兼容，因为底层输出仍然可以复用 `tg-rcore-tutorial-console` 的日志能力，而不需要额外引入复杂依赖。

本模块的阶段性实施规划如下：

1. 在 `ch3` 中统一记录 syscall 次数、调度切换和时钟中断；
2. 在 `ch4` 中统一记录缺页、地址翻译失败和权限异常；
3. 在 `ch8` 中统一记录锁竞争、阻塞、唤醒和死锁检测结果。

这样做的好处是，不同章节虽然主题不同，但都能通过同一日志接口输出“关键教学现象”。

#### 模块 B：更强的测试体系

当前仓库已具备 `test.sh + tg-rcore-tutorial-checker` 的基本测试闭环，这为进一步增强测试提供了很好的基础。我的改造思路不是替换现有测试，而是在其基础上叠加两类能力。

第一类是“最小可行的内核自检”：

- 编译期检查：确保关键特性开关和章节构建路径不被破坏；
- 运行期自检：在内核启动后执行少量不依赖用户态的 sanity check，例如上下文初始化、页表建立后的关键映射断言、同步原语初始状态检查等。

第二类是“脚本化的 userland 回归测试增强”：

- 对现有 `test.sh` 做统一包装，使输出更稳定、更便于定位失败点；
- 对章节测试结果增加“失败分类”，区分构建失败、QEMU 启动失败、功能失败、输出不匹配；
- 为回归测试补充“关键指标摘要”，不仅给出 pass/fail，还给出触发了哪些核心行为。

这样改造后，测试就不只是“批改作业”，而会更像一套教学实验验证工具。

#### 模块 C：更好的调试体验

这是我认为当前教程最值得做、也最容易让后续同学受益的部分。

现有教程已经有不错的 README 和日志输出，但调试经验大多分散在源码、错误输出和个人实践中。T8 的目标是把这些经验提炼成可以直接复用的“调试手册”。

我的设计包括：

- 为每个代表性章节配一个“常见 bug 清单”；
- 为每类 bug 配一个“定位方法”；
- 明确区分三类调试工具：日志、QEMU 输出、GDB 断点。

例如：

- `ch3` 中常见问题可以包括：时钟中断未开启、`sepc` 未移动导致重复 syscall、任务状态未切换导致假死；
- `ch4` 中常见问题可以包括：页表权限错误、地址翻译失败、缺页后返回地址错误；
- `ch8` 中常见问题可以包括：线程阻塞后未重新入队、unlock 顺序错误导致“丢唤醒”、死锁检测状态未及时更新。

对应的定位方法应当标准化，例如：

- 先看 `scause/stval/sepc`；
- 再看当前 task/proc/thread 状态；
- 最后检查 ready queue、wait queue、资源占有关系是否一致。

这样改造的意义在于，把调试经验从“个别同学掌握的技巧”变成“教程的一部分”。

#### 模块 D：文档模板重构

我计划把每个实验章节的文档结构尽量统一为如下模板：

1. 学习目标；
2. 关键概念；
3. 关键代码入口；
4. 常见坑；
5. 测试与指标；
6. 思考题。

这种模板不是为了形式统一，而是为了降低阅读切换成本。当前教程每章内容都较充分，但学生跨章阅读时，仍然需要重新适应不同章节的叙事节奏。统一模板后，读者会更快建立稳定预期：

- 先知道这一章要学什么；
- 再知道从哪里看代码；
- 然后知道怎么验证自己做对了；
- 最后知道哪几个地方最容易出错。

这也是我选择工程质量方向的重要原因：它直接提升后续所有章节的学习效率，而不是只服务某一个新功能。

## 三、个性化教程方案的具体落地设计

### 3.1 主线实验设计

为了让 T8 不停留在“文档建议”，我把它设计为一个可落地的三阶段主线实验。

#### 第一阶段：统一日志入口

目标是在不大改各章代码结构的前提下，把关键事件都路由到统一日志接口中。

实施重点：

- 复用 `tg-rcore-tutorial-console` 作为统一输出后端；
- 设计轻量级事件标签，如 `[SC]`、`[TRAP]`、`[SCHED]`、`[VM]`、`[SYNC]`；
- 保留现有人类可读日志风格，不强行引入重型序列化格式；
- 增加少量统计器，用于在章节结束时打印摘要。

验收标准：

- `ch3` 能看到 syscall、yield、timer interrupt 的统一格式输出；
- `ch4` 能看到页异常和地址翻译失败的统一格式输出；
- `ch8` 能看到锁阻塞、唤醒、死锁拒绝的统一格式输出。

#### 第二阶段：统一测试与回归

目标是让“运行实验”从手工观察输出，升级为可重复的脚本化流程。

实施重点：

- 保留 `test.sh` 作为章节入口；
- 基于 `tg-rcore-tutorial-checker` 增加更细的失败分类；
- 每章增加最少一组“回归前后对照点”，例如：
  - 是否触发预期 trap；
  - 是否记录到预期调度事件；
  - 是否输出同步原语的阻塞/唤醒摘要。

验收标准：

- 学生不仅知道“没过”，还能知道“构建没过”“运行没起”“行为不对”；
- 同一测试可以重复运行，输出结构稳定；
- 报告中可以直接引用测试结果作为量化依据。

#### 第三阶段：调试与文档整合

目标是把实验过程中最有价值的调试经验沉淀为教程资产。

实施重点：

- 为 `ch3/ch4/ch8` 分别整理“常见 bug - 现象 - 诊断 - 修复路径”；
- 在章节文档中增加“建议先读哪些源码文件”的导航；
- 为每章添加“测试与指标”和“思考题”固定小节。

验收标准：

- 新同学遇到问题时，不需要只靠搜索聊天记录或反复试错；
- 文档能够同时服务“第一次做实验的人”和“复习代码结构的人”；
- 调试方法本身成为教学内容的一部分。

### 3.2 支线实验设计

在主线之外，我还设计了两个可选支线，用作后续扩展：

- 支线 1：为 `ch5` 的调度实验增加“公平性和等待时间”指标输出；
- 支线 2：为 `ch8` 的同步实验增加“锁竞争次数、阻塞次数、最大等待时间”统计。

这两个支线不要求当前一次性全部完成，但它们与主线的 tracing/metrics 方案天然兼容，后续扩展成本较低。

### 3.3 本次已经完成的实现与实际表现

为了让 T8 不只停留在设计层，我在当前仓库中已经完成了一轮实际改造。已完成内容主要分为四类。

#### 1. 实现统一事件日志接口

我在 `tg-rcore-tutorial-console` 中新增了统一事件日志和指标摘要接口，使不同章节可以用统一格式输出关键行为。

已完成的接口包括：

- `event!`：输出结构化事件日志；
- `metric!`：输出结构化指标摘要；
- 对应的底层函数 `emit_event` / `emit_metric`。

实际表现：

- 日志中会出现统一格式的事件行，例如：
  - `[EVENT][ch3][schedule] task=1 timer-expired`
  - `[EVENT][ch4][vm] proc=head trap=LoadPageFault ...`
  - `[EVENT][ch8][sync] mutex_lock mutex=0 tid=3 blocked`
- 章节结束时会输出统一格式的指标摘要，例如：
  - `[METRIC][ch3][timer_events] ...`
  - `[METRIC][ch4][vm_fault_events] ...`
  - `[METRIC][ch8][sync_blocked_events] ...`

这意味着后续无论是人工阅读日志，还是脚本筛选事件，都不需要再依赖每章各自不同的输出风格。

更具体地说，这些日志不是停留在概念层，而是已经在代码里被真正调用。例如：

- 在 `tg-rcore-tutorial-ch3/src/main.rs` 中，当任务时间片到期时，会输出：
  - `[EVENT][ch3][schedule] task=0 timer-expired`
- 在 `tg-rcore-tutorial-ch3/src/main.rs` 中，当任务主动 `yield` 时，会输出：
  - `[EVENT][ch3][schedule] task=2 yield`
- 在 `tg-rcore-tutorial-ch4/src/main.rs` 中，当发生页异常时，会输出类似：
  - `[EVENT][ch4][vm] proc=head trap=LoadPageFault stval=0x... sepc=0x...`
- 在 `tg-rcore-tutorial-ch8/src/main.rs` 中，当线程拿不到互斥锁被阻塞时，会输出：
  - `[EVENT][ch8][sync] mutex_lock mutex=0 tid=3 blocked`
- 在 `tg-rcore-tutorial-ch8/src/main.rs` 中，当死锁检测拒绝一次资源申请时，会输出：
  - `[EVENT][ch8][sync] sem_down sem=1 tid=4 deadlock`

这些例子说明，T8 不是“打算以后统一日志”，而是已经把统一日志接口真正接入了运行时关键路径。

#### 2. 在代表性章节接入 tracing / metrics

我没有一次性改完全部章节，而是选择了最能体现 T8 价值的三个样板章节：

- `ch3`：调度与 syscall 路径；
- `ch4`：虚存与异常路径；
- `ch8`：同步、阻塞、唤醒与死锁检测路径。

已完成的具体接入如下：

- `ch3`
  - 记录 timer interrupt、普通 syscall、yield、exit、异常杀死任务；
  - 统计 `timer_events / syscall_events / yield_events / exit_events / killed_events`。
- `ch4`
  - 记录 syscall、进程退出、unsupported syscall；
  - 区分记录普通 trap 和 VM 相关 fault；
  - 统计 `syscall_events / vm_fault_events / killed_processes`。
- `ch8`
  - 记录 semaphore / mutex / condvar 的阻塞、唤醒、获取成功、死锁拒绝；
  - 统计 `sync_blocked_events / sync_wake_events / sync_deadlock_rejections / sync_wait_events`。

这些改动的实际效果是，原本需要靠阅读源码和零散 `log::info!` 才能推断的运行时状态，现在可以直接在日志里看到。例如：

- 在 `ch3` 中，学生可以直接看到任务是因为时间片到期被切走，还是因为 `yield` 主动让出 CPU；
- 在 `ch4` 中，学生可以直接区分“普通异常”与“页异常”，并同时看到 `stval` 和 `sepc`；
- 在 `ch8` 中，学生可以直接看到线程是在哪个锁或信号量上被阻塞、由谁唤醒，以及死锁检测是否拒绝了本次资源请求。

这使得“看现象猜机制”的学习方式，真正变成“看事件对照机制”。

为了让这个说法更具体，下面给出三个“学生真正能看到什么”的例子。

示例一：`ch3` 的调度路径

- 原来：只能在混杂日志中看到某个 `app{i} timeout`，不容易把它与统一的教学指标联系起来。
- 现在：除了原有日志，还会额外看到
  - `[EVENT][ch3][schedule] task=1 timer-expired`
  - `[EVENT][ch3][schedule] task=1 yield`
  - `[METRIC][ch3][timer_events] 37`
  - `[METRIC][ch3][yield_events] 12`
- 教学意义：学生不但知道“发生了调度”，还知道“是抢占式切换还是协作式让出”，并且能看到整章结束后的统计值。

示例二：`ch4` 的虚存异常路径

- 原来：遇到页异常时，更多依赖 `unsupported trap: ...` 这种错误输出，信息粒度不稳定。
- 现在：会统一输出
  - `[EVENT][ch4][vm] proc=head trap=LoadPageFault stval=0x80401234 sepc=0x10074`
  - `[METRIC][ch4][vm_fault_events] 3`
- 教学意义：学生可以直接把 `trap 类型 + stval + sepc` 与缺页或权限异常联系起来，减少“看着 panic 不知道从哪查”的情况。

示例三：`ch8` 的同步阻塞路径

- 原来：需要同时追踪 wait queue、阻塞态和解锁路径，才能大致猜到线程为什么卡住。
- 现在：会直接输出
  - `[EVENT][ch8][sync] mutex_lock mutex=0 tid=3 blocked`
  - `[EVENT][ch8][sync] mutex_unlock mutex=0 wake_tid=3`
  - `[EVENT][ch8][sync] condvar_wait cv=0 mutex=0 tid=3 wake_tid=5 reacquired=false`
  - `[METRIC][ch8][sync_blocked_events] 9`
- 教学意义：学生可以很直观地看到“阻塞发生在哪里、谁负责唤醒、唤醒后是否重新获取到了锁”。

#### 3. 增强 checker 的失败提示能力

我在 `tg-rcore-tutorial-checker` 中补充了失败分类信息，不再只输出一个总的 `FAILED`。

新增能力包括：

- 区分 `missing expected patterns`；
- 区分 `forbidden patterns found`；
- 当输出为空时提示 `output was empty`。

实际表现：

- 如果测试根本没有进入内核主流程，checker 会提示“输出为空”，学生可以优先排查构建、QEMU 启动或早期 panic；
- 如果功能路径没走到，checker 会提示“缺少 expected pattern”，学生可以优先回看事件日志和对应 trap/syscall 分支；
- 如果出现错误输出，checker 会提示“命中了 forbidden pattern”，更利于快速缩小排查范围。

这项改造虽然代码量不大，但对调试体验提升非常明显，因为它把“只有 FAIL”的粗粒度反馈变成了“知道失败属于哪一类”的反馈。

一个已经实际出现过的例子是：我在 Docker 中尝试运行 `ch3` 的 `./test.sh base` 时，checker 没有只给出一个模糊的 `FAILED`，而是结合输出表明当前问题属于“构建链路未完成”，继续追踪后定位到容器里缺少 `cargo-clone`。这说明增强后的测试体系确实能够帮助缩小故障范围。

实际表现：

- 后续重构章节 README 时，不再需要每章从零组织结构；
- 当实验失败时，学生可以优先按调试手册给出的顺序检查 `scause/stval/sepc`、队列状态和事件日志，而不是盲目试错。

#### 5. 已完成的验证结果

为了证明这些改造不是只停留在文字层，我还对代码做了实际验证。

已完成验证如下：

- 在 `rcore-docker` 环境中完成 `cargo +stable check`：
  - `tg-rcore-tutorial-console`
  - `tg-rcore-tutorial-checker`
  - `tg-rcore-tutorial-ch3`
  - `tg-rcore-tutorial-ch4`
  - `tg-rcore-tutorial-ch8`
- 在同一 Docker 环境中完成基于 `scripts/t8-regression.sh` 的运行时回归：
  - `ch3` 看到 `T8 ch3 observe OK!`
  - `ch4` 看到 `T8 ch4 vm observe OK!`
  - `ch8` 看到 `T8 ch8 Usertests passed!`
- 三章运行时日志中都成功匹配到了对应的 `[EVENT]` / `[METRIC]` 证据：
  - `ch3`：`[EVENT][ch3][schedule] ...`、`[METRIC][ch3][timer_events] ...`
  - `ch4`：`[EVENT][ch4][vm] ...`、`[METRIC][ch4][vm_fault_events] ...`
  - `ch8`：`[EVENT][ch8][sync] condvar_wait ...`、`[EVENT][ch8][sync] deadlock-detect enabled=true`、`[METRIC][ch8][sync_blocked_events] 2`

在这个验证过程中，我还顺手修复了两处原本就会妨碍 user workload 落地的工程问题：

- `tg-rcore-tutorial-syscall/src/user.rs` 中的 `asm!("ecall")` 调用补上了显式 `unsafe` 块，解决了 2024 edition 下 user 程序构建被 `unsafe_op_in_unsafe_fn` 卡住的问题；
- `scripts/t8-regression.sh` 明确设置了 `TG_USER_DIR`，避免章节构建脚本退回到 `cargo-clone` 分支；同时增加了 `grep` fallback 和 `CHAPTER=t8-8` 的独立 ch8 回归入口。

因此，从“已经完成了哪些实现”这个角度看，T8 已经不仅是一个设计方案，而是一个有具体代码、有具体表现、有 Docker 运行验证结果的工程化增强案例。

## 五、与 AI 合作的实现过程

`TASK2.md` 强调需要写出与 AI 合作的过程，因此本节不只是描述“我用了 AI”，而是说明 AI 在工程工作流中的具体角色。

### 5.1 我如何与 AI 分工

在这次 T8 设计中，我把自己定位为：

- 需求定义者；
- 方案裁剪者；
- 最终实现与验证负责人。

把 AI 定位为：

- 代码与文档结构分析助手；
- 架构设计参谋；
- 调试路径建议器；
- 报告撰写辅助工具。

这种分工的原因是，教学实验改造不像刷题那样只有唯一答案。AI 可以很快提出很多改造点，但哪些点真正适合当前仓库、哪些点会把工作量推到不可控，需要我结合代码结构和任务时间做裁剪。

### 5.2 AI 在本任务中的具体帮助

#### 帮助 1：快速建立对仓库结构的全局认识

面对 `tg-rcore-tutorial` 这样的多 crate 教学仓库，如果纯手工阅读，很容易陷入“只看当前章节、忽略公共组件”的局部视角。AI 可以先帮我梳理：

- 哪些公共 crate 是日志、调度、同步、测试的支撑点；
- 哪些章节已经具备可观测性雏形；
- 哪些改造点可以复用现有模块，而不是另起新系统。

例如，在分析过程中，我重点确认了：

- `tg-rcore-tutorial-console` 已经提供统一日志出口；
- `tg-rcore-tutorial-checker` 已经提供脚本化输出校验能力；
- `ch3/task.rs` 已经有 syscall 计数，说明 tracing 可以从现有能力演化。

这类工作如果完全人工完成会比较慢，而 AI 很适合先帮我快速定位切入口。

#### 帮助 2：把“改进想法”收束为可交付方案

最开始我也考虑过更大、更“亮眼”的题目，例如可插拔调度器、多核、中断响应扩展等。但 AI 在反复对比后帮助我确认了一点：

**如果目标是先完成一个高质量、可提交、可解释的个性化教程案例，那么 T8 更适合作为第一项任务。**

因为它可以借助现有仓库完成较大幅度的“学习体验提升”，同时又不会把实现范围扩展到体系结构级重构。

这个判断对我很重要。它不是 AI 直接替我做决定，而是 AI 帮我快速比较了不同任务的工作量、复用程度和报告压力，帮助我收敛选题。

#### 帮助 3：协助形成“可验证的报告结构”

如果只靠个人写作，报告容易变成泛泛而谈的心得总结。AI 的价值在于帮助我把报告结构压实为：

- 设计目标；
- 现有问题；
- 具体改造点；
- 与仓库对应关系；
- 实施路径；
- 学习效果评估。

这使得报告更接近真实的软件工程设计文档，而不是单纯课程感想。

### 5.3 与 AI 协作中遇到的问题与修正过程

在使用 AI 的过程中，也出现了几个典型问题。

第一个问题是“AI 过于乐观地估计工作量”。例如多核、中断、虚存置换、实时调度这些题，从描述上看都很吸引人，但一旦落实到 `tg-rcore-tutorial` 现有结构，就会迅速膨胀为大改动。我的修正方式是：要求 AI 回到代码仓库本身，优先依据当前模块和现成测试来评估，而不是只看题目名称。

第二个问题是“AI 容易给出太泛的改进建议”。例如“增强测试”“改进文档”这类建议如果不落到具体 crate、具体章节、具体脚本上，就缺乏可执行性。我的修正方式是让 AI 明确绑定：

- 哪个公共组件负责承接改造；
- 哪个章节最适合做样板；
- 哪种指标最容易先落地。

第三个问题是“AI 擅长提出方向，但不自动替我做范围控制”。我在使用过程中逐步明确了一个规则：

**任何提议都必须能在当前仓库中找到直接映射的文件或流程，否则不进入本轮交付。**

这条规则对防止任务失控很有帮助。

### 5.4 本次与 AI 协作的经验总结

通过这次 T8，我对与 AI 协作有两个更明确的认识。

第一，AI 最适合做“高维搜索 + 方案收敛”的辅助，而不是替代最终判断。它可以帮我快速遍历可能路径，但需要我用代码结构、课程目标和时间约束做最后裁剪。

第二，在操作系统实验这种强工程、强上下文的任务里，AI 的价值不只是生成代码，更重要的是：

- 帮我建立全局视角；
- 帮我把模糊想法变成结构化方案；
- 帮我把调试与文档工作系统化。

## 六、学习效果评估

### 6.1 定量评估

虽然 T8 当前阶段主要是设计和工程方案收敛，但依然可以给出清晰的量化评估维度。相比原始教程，我计划用以下指标衡量改造效果：

| 维度 | 原教程现状 | T8 改造后的目标 |
|---|---|---|
| 可观测性覆盖 | 日志分散在各章实现中 | `syscall/trap/schedule/vm/sync` 使用统一事件接口 |
| 测试输出粒度 | 以 pass/fail 为主 | 增加失败分类和关键事件摘要 |
| 调试资料组织度 | README 和源码中分散存在 | 每章附带结构化 bug 清单和定位方法 |
| 文档模板一致性 | 章节风格接近但粒度不完全一致 | 统一为“目标-代码点-坑点-测试-思考题”模板 |
| 可复用性 | 改进经验依赖个人积累 | 公共 crate + 文档规范可跨章复用 |

如果后续继续实施代码层改造，还可以进一步统计：

- `ch3` 的 syscall/schedule 事件覆盖率；
- `ch4` 的页异常日志覆盖率；
- `ch8` 的同步阻塞/唤醒事件覆盖率；
- 各章测试脚本的回归耗时和失败定位耗时。

### 6.2 定性评估

从学习效果看，T8 对我的提升主要体现在三个方面。

第一是系统理解方式发生了变化。以前我更容易把每一章当作独立作业去做，现在我会更主动地问：

- 这一章最关键的运行时状态是什么；
- 这些状态能不能被观测到；
- 出错时应该先看哪个数据结构、哪个寄存器、哪个队列。

第二是工程意识增强。原来我更关注“代码是否跑通”，现在我更关注：

- 是否有统一日志入口；
- 是否有稳定测试脚本；
- 是否能快速复现和定位 bug；
- 文档是否足以支持下一个人重复学习过程。

第三是对“教学实验设计”这件事本身理解更深。以前我倾向于把实验理解为功能实现；现在我更清楚，一个好的实验教程还应该包含：

- 清晰的阅读路径；
- 明确的验证标准；
- 可迁移的调试经验；
- 可以复用的工程骨架。

### 6.3 成本与不足

T8 的价值很高，但也有代价。

- 它不像新增一个功能那样能快速展示“炫酷结果”，更多收益体现在后续章节学习效率上；
- 它需要较强的抽象能力，要在不破坏现有教学主线的前提下做规范化改造；
- 它的成果一部分是“减少未来排错成本”，这类收益短期不如新功能那样直观。

但我认为，这些代价是值得的。因为操作系统实验本身就不应该只训练“把代码拼出来”，还应该训练“如何构造一个可维护的系统”。

### 6.4 与现有教学实验教程的对比分析

与当前仓库相比，我设计的 T8 改造方案主要有四点差异：

第一，原教程的强项在于章节演进清晰、代码组织较规范；T8 进一步强调“跨章节的统一工程规范”。

第二，原教程已经有日志、测试和 README，但这些能力还没有被整合为一套“可观测 - 可验证 - 可调试”的完整体系；T8 正是在这一点上补足闭环。

第三，原教程更偏向“教你把功能做出来”；T8 希望进一步做到“教你如何判断自己真的做对了，以及做错后如何定位”。

第四，原教程已经适合课程教学；T8 的改造方向则更适合“自学 + 与 AI 协作”的学习方式，因为它把问题拆成了更可交互、更可验证的小单元。

## 七、实施计划与最终交付形式

为了让这份报告不仅停留在设计层，我将 T8 的后续交付拆分为以下几个可执行产物：

1. `docs/task2-t8-report.md`
   本文，即设计总结报告。

2. 文档模板升级
   优先在 `ch3/ch4/ch8` 三章试点统一“目标 → 关键代码点 → 常见坑 → 测试与指标 → 思考题”结构。

3. tracing/metrics 轻量化试点
   先在 `ch3` 统一 syscall 与调度事件，再扩展到 `ch4` 和 `ch8`。

4. 测试脚本增强
   基于现有 `test.sh` 与 `tg-rcore-tutorial-checker` 增加更明确的失败分类与运行摘要。

5. 常见 bug 清单
   为 `ch3/ch4/ch8` 分别整理一页结构化定位手册。

这样设计的好处是，即使时间有限，也可以优先完成最关键的 20% 改造，获得 80% 的教学体验提升。

其中，当前已经完成的交付包括：

- `docs/task2-t8-report.md`
- `docs/t8-debug-playbook.md`
- `docs/t8-chapter-template.md`
- `tg-rcore-tutorial-console` 中的统一事件/指标接口
- `ch3/ch4/ch8` 的代表性 tracing/metrics 接入
- `tg-rcore-tutorial-checker` 的失败分类增强

## 八、结论

本次 T8 不是在 `tg-rcore-tutorial` 中加入一个新的操作系统大功能，而是从工程质量角度对现有教程做一次个性化重构。它的核心价值在于：

- 让实验更可观测；
- 让测试更可复现；
- 让调试更有方法；
- 让文档更有教学一致性。

这项改造符合我的学习方式，也符合 `TASK2.md` 中强调的“与 AI 合作、形成个性化教程设计”的目标。相比直接追求更复杂的新功能，T8 更能体现我对教学实验“如何被设计得更适合学习”的理解。

如果后续继续推进实现，我希望把 T8 做成一个真正可被复用的工程化教学增强层，让 `tg-rcore-tutorial` 不只是“能跑的教程”，而成为“能看、能测、能调、能比较”的实验平台。
