# T8 章节文档模板

这份模板用于统一后续章节的实验文档结构，目标是降低跨章节阅读成本，并让每一章都具备“目标 - 代码 - 测试 - 调试 - 反思”的完整闭环。

## 1. 学习目标

- 本章核心机制是什么？
- 完成本章后应能解释哪些关键概念？
- 需要观察到哪些运行时现象？

## 2. 关键概念

- 用不超过半页的文字概括本章的核心抽象；
- 不追求百科式解释，重点说明它与前一章相比新增了什么；
- 若有多个新概念，建议用 3 到 5 个短条目概括。

## 3. 关键代码入口

建议给出固定顺序的源码阅读入口，并解释每个入口解决什么问题。

示例格式：

| 阅读顺序 | 文件 | 重点问题 |
|---|---|---|
| 1 | `src/main.rs` | 系统主流程如何组织？ |
| 2 | `src/process.rs` | 关键数据结构如何建模？ |
| 3 | `src/processor.rs` | 状态切换与调度如何发生？ |

## 4. 常见坑

每个坑点建议固定写四项：

- 症状
- 高概率原因
- 建议先看哪里
- 如何验证修复是否有效

## 5. 测试与指标

本节建议同时包含“怎么跑”和“看什么”。

至少应回答：

- 使用哪条命令运行？
- 通过的判据是什么？
- 应该观察哪些事件日志或指标摘要？

示例：

```bash
./test.sh base
./test.sh exercise
```

## 6. 思考题

思考题不追求数量多，而应引导学生把“功能实现”上升到“设计权衡”。

示例：

- 如果把 FIFO 调度改成优先级调度，需要补哪些状态？
- 为什么 `condvar_wait` 通常要放在 `while` 而不是 `if` 中？
- 为什么统一日志接口会提高调试效率，但也可能增加运行期开销？

## 7. 可选补充：调试建议

若本章机制复杂，建议再增加一小节：

- 先看哪些寄存器
- 再看哪些队列或状态位
- 需要时再使用 GDB / QEMU log

这样文档就不只是“告诉你做什么”，而是“告诉你出错后怎么找”。
