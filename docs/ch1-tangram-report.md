# `ch1-tangram` 游戏实验独立总结报告

## 1. 实验背景与任务理解

本实验对应 `tg-rcore-tutorial` 根目录 `README.md` 中给出的 `ch1-tangram` 要求：

> 在 ch1 基础上扩展内核功能，静态显示七巧板“OS”图案，即基于 VirtIO-GPU 驱动操作 Framebuffer，将 OS 的代码中数组定义的七巧板“OS”图案像素数据直接渲染到帧缓冲，实现静态图片显示。

我对这个要求的理解是：

1. 不能只停留在 `Hello, world!` 串口输出层面，而是要真正把 `ch1` 从“最小字符输出内核”扩展成“最小图形输出内核”。
2. 核心任务不是做交互游戏逻辑，而是在 `ch1` 极简条件下打通一条完整的图形显示路径：
   - QEMU 提供 VirtIO-GPU 设备
   - 内核识别并初始化 VirtIO-GPU
   - 建立 framebuffer
   - 将代码中的图形数据转换为像素
   - 写入帧缓冲并显示在屏幕上
3. 由于 `ch1` 还没有分页、文件系统、进程管理和成熟的堆内存系统，因此这次实现必须尽量保持“极简但完整”，不能照搬高章节的大型内核结构。

因此，我给自己设定的实验目标不是“简单把一张图片贴上去”，而是：

> 在不破坏 `ch1` 教学定位的前提下，为 `ch1` 补上一条最小可运行的 VirtIO-GPU + framebuffer 渲染链路，并成功静态显示七巧板 “OS” 图案。

## 2. 实验目标

本次 `ch1-tangram` 独立实验的具体目标如下：

1. 从原始 `tg-rcore-tutorial-ch1` 切出独立分支，避免影响其他实验。
2. 让 `cargo run` 不再只打开串口，而是能启动带图形窗口的 QEMU。
3. 在 `ch1` 中新增 VirtIO-GPU 驱动初始化能力。
4. 在没有现成堆管理器和页表管理的条件下，为 VirtIO 驱动补足最小 DMA/堆分配支持。
5. 将七巧板 “OS” 图形数据写在代码中，并渲染到 framebuffer。
6. 完成可复现的本地验证，确保图片能够正常显示。
7. 形成一份独立实验报告，清晰说明实现内容、AI 协作过程、问题修复过程与学习效果。

## 4. 我实际完成了哪些工作

这一部分是本报告最核心的内容，用来明确回答“我到底做了什么”。

### 4.1 扩展了 `ch1` 的运行方式

原始 `ch1` 的运行方式是：

- 使用 `-nographic`
- 所有输出只走串口
- 只能在终端里打印 `Hello, world!`

为了支持 `tangram` 图形显示，我修改了 `tg-rcore-tutorial-ch1/.cargo/config.toml`，将运行方式改为：

- 保留串口输出到终端：`-serial stdio`
- 关闭 QEMU monitor 对标准输入输出的占用：`-monitor none`
- 在 `virtio-mmio-bus.0` 上挂载 VirtIO-GPU 设备：
  `-device virtio-gpu-device,bus=virtio-mmio-bus.0`

修改后，`cargo run` 会同时具备两种能力：

1. 串口输出调试信息
2. 打开图形窗口显示 framebuffer 内容

这一步非常关键，因为如果 QEMU 仍然是 `-nographic`，后面的 framebuffer 渲染即使成功，也没有图形窗口可以看见效果。

### 4.2 为 `ch1` 引入了 VirtIO-GPU 驱动能力

原始 `ch1` 的依赖只有 `tg-sbi`，没有任何图形设备支持。

我在 `tg-rcore-tutorial-ch1/Cargo.toml` 中新增：

```toml
virtio-drivers = "0.1.0"
```

然后在 `src/main.rs` 中接入了 `virtio_drivers::VirtIOGpu`，完成了以下流程：

1. 通过 VirtIO MMIO 基地址 `0x1000_1000` 创建 `MmioTransport`
2. 基于该 transport 初始化 `VirtIOGpu`
3. 读取显示分辨率
4. 建立 framebuffer
5. 在 framebuffer 中绘制图形
6. 调用 `flush()` 将图像刷新到屏幕

这意味着 `ch1` 已经不再是“只会输出字符”的最小内核，而是具备了最基础的图形显示能力。

### 4.3 自行补充了 `ch1` 缺失的最小内存支持

`ch1` 的难点不在“API 会不会调”，而在于它太简化了。相比后面章节，本章没有：

- 完整堆分配器
- 虚拟内存管理
- 页表地址翻译
- 高级内核基础设施

但是 `virtio-drivers` 在内部依赖 `alloc`，并且驱动需要 DMA 连续内存，因此我做了两件事情。

#### 4.3.1 实现了静态 DMA Arena

我在 `src/main.rs` 中定义了页对齐的静态 DMA 区域，并通过 `AtomicUsize` 实现了最小 bump allocator，用于：

- VirtIO 队列所需内存
- framebuffer 所需 DMA 空间

设计思路是：

1. 在 `.bss.uninit` 中预留一大片连续内存
2. 每次按页递增分配
3. 当前实验中不做复杂回收，只保证“能稳定运行”

这样做的优点是：

- 实现简单，适合 `ch1`
- 不依赖更高章节的内存管理系统
- 与“最小裸机实验”的教学目标一致

#### 4.3.2 实现了最小全局堆分配器

第一次编译时，我遇到的第一个实际错误是：

```text
no global memory allocator found but one is required
```

这说明仅仅引入 `virtio-drivers` 还不够，因为它依赖 `alloc`，而 `ch1` 原本根本没有全局分配器。

为此，我又在 `main.rs` 中补了一个最小 `BumpAllocator`，同样基于静态数组和原子偏移实现。这不是一个通用堆分配器，但对本实验足够：

- 分配次数有限
- 生命周期贯穿整个内核运行过程
- 无需复杂释放逻辑

这一步使 `virtio-drivers` 能够在 `ch1` 中顺利编译和运行。

### 4.4 新增了 framebuffer 绘制模块

我单独新增了：

- `tg-rcore-tutorial-ch1/src/framebuffer.rs`

该模块提供了最小图形绘制能力，包括：

1. `FrameBuffer` 封装
2. `clear()` 清屏
3. `set_pixel()` 单像素写入
4. `fill_triangle()` 三角形填充
5. `fill_convex_polygon()` 凸多边形填充

这里的设计目的不是追求复杂图形学功能，而是为七巧板图案提供足够的绘制能力。

七巧板本质上可以拆解为若干个三角形、四边形和菱形，因此“凸多边形填充”已经可以很好地支持本实验。

### 4.5 新增了七巧板 “OS” 图案数据模块

我单独新增了：

- `tg-rcore-tutorial-ch1/src/tangram.rs`

这个模块中定义了七巧板图案所需的图形数据，包括：

- O 字母部分的若干块图形
- S 字母部分的若干块图形
- 各个部分的颜色
- 逻辑坐标到实际分辨率的缩放与居中计算

需要说明的是：

本实验采用的是“代码中的多边形顶点数组 + 软件光栅化到像素”的实现方式，而不是直接手写一整张超大的像素数组。

我这样做的原因是：

1. 直接手写整张像素数组过于冗长，可读性很差
2. 七巧板图形天然适合用几何顶点表示
3. 从教学角度看，顶点数组更能体现“图形如何被转换成像素”的过程

因此，本实验虽然没有逐项手写完整像素表，但本质上仍然满足了“代码中定义图形数据，最终写入 framebuffer 形成静态图像”的实验目标。

### 4.6 完善了串口输出与退出流程

为了方便验证，我没有让程序显示后立即退出，而是在渲染完成后通过串口打印：

3. 串口日志可以帮助判断问题出在“驱动初始化”还是“图形绘制”阶段

### 4.7 同步更新了文档和测试脚本

测试脚本改为自动输入 `q`，从而验证：

## 5. 关键实现思路

### 5.1 为什么 `ch1` 适合做静态 Tangram

我认为 `ch1` 最适合的游戏型实验并不是需要输入和调度的动态游戏，而是“静态图形显示”，原因如下：

1. `ch1` 还没有进程管理、时钟中断、系统调用框架等复杂能力。
2. 如果在 `ch1` 直接实现需要交互的游戏，会引入大量额外机制，容易偏离本章主题。
3. Tangram 的静态显示恰好只要求：
   - 裸机启动
   - 设备初始化
   - 像素绘制
   - 图形输出

所以它是一个非常适合 `ch1` 的“低耦合图形实验”。

### 5.2 为什么采用“最小驱动链路”而不是移植高章节框架

我没有直接搬 `ch6` 之后的 MMIO、页表、堆管理做法，而是为 `ch1` 单独写了最小版本。原因是：

1. `ch1` 的教学定位就是“最小执行环境”
2. 如果直接照搬高章节基础设施，会让 `ch1` 失去简洁性
3. 老师看 `ch1-tangram`，重点应该是“在极简环境里增加图形输出”，而不是“提前引入后面章节的一整套系统”

因此，本次实现的原则是：

> 只补完成 `tangram` 所必须的最小功能，不把 `ch1` 改造成一个过度复杂的内核。

### 5.3 为什么采用多边形数组表示图案

七巧板图案本身由几何块组成，因此使用顶点数组表示具有明显优点：

1. 数据量更小
2. 修改颜色、位置、大小更方便
3. 更符合“七巧板是由几何块拼成”的直观认知
4. 能顺带练习 framebuffer 光栅化和像素写入

如果未来老师更倾向于“像素数组直接拷贝”的版本，这一版也可以继续演化：先离线生成像素表，再直接写入 framebuffer。但从当前实验目标来看，多边形数组方案已经足够清晰、可控、可验证。

## 7. 实际遇到的问题、Bug 与解决过程

### 7.1 图形模式与串口模式冲突

#### 现象

原始 `ch1` 使用 `-nographic`，这会让 QEMU 不打开图形窗口。

#### 分析

即使 framebuffer 写成功，只要 QEMU 不提供图形窗口，用户也无法看到图像。

#### 解决

将 runner 改为图形模式，同时保留 `-serial stdio`，实现“图形窗口 + 串口日志”双通道。

### 7.2 驱动依赖 `alloc`，而 `ch1` 没有堆分配器

#### 现象

`cargo build` 报错：

```text
no global memory allocator found but one is required
```

#### 分析

`virtio-drivers` 依赖 `alloc`，但原始 `ch1` 只有最小裸机入口，没有堆分配系统。

#### 解决

实现基于静态数组的最小 `BumpAllocator`，只满足本实验需要，不额外引入复杂基础设施。

### 7.3 `ch1` 没有 DMA 管理能力

#### 现象

VirtIO 队列和 framebuffer 都需要 DMA 连续内存，而 `ch1` 没有现成支持。

#### 分析

如果没有 DMA 分配逻辑，VirtIO-GPU 驱动就无法正常工作。

#### 解决

手动实现静态 DMA Arena，以页为单位递增分配，保证驱动运行所需内存。

### 7.4 严格告警配置导致的编译收口问题

#### 现象

由于 `ch1` 开启了：

```rust
#![deny(warnings, missing_docs)]
```

一些仅用于对齐的包装结构触发了 `dead_code` 警告，导致编译失败。

#### 分析

这不是功能性错误，而是工程规范导致的收口问题。

#### 解决

针对这类结构局部加了 `#[allow(dead_code)]`，避免无意义的告警阻塞构建。

### 7.5 如何让老师或开发者方便验收

#### 问题

如果程序显示后立即退出，老师很难亲自确认图像效果。

#### 解决

增加串口提示和 `q` 退出逻辑，并修改 `test.sh` 自动输入 `q`，兼顾：

1. 人工验收
2. 自动化测试

## 9. 学习效果评估

原始要求中明确提出要评估学习效果，并与本校现有教学实验教程做定量/定性对比。下面是我的真实评价。

### 9.1 知识方面的提升

本实验让我在以下几个方面有了明显提升。

#### 9.1.1 对 `ch1` 的理解从“能打印字符”提升到“最小内核如何驱动设备”

原来我对 `ch1` 的理解主要停留在：

- `no_std`
- `no_main`
- `_start`
- SBI 输出

做完 `ch1-tangram` 后，我对 `ch1` 的理解变成了：

- `ch1` 其实是一个可以继续扩展的最小内核骨架
- 即使没有复杂基础设施，也可以逐步加入设备驱动能力
- 图形输出本质上仍然是“硬件初始化 + 内存写入 + 设备刷新”

这让我对“操作系统如何从极小内核逐步长出功能”有了更直观的认识。

#### 9.1.2 对 VirtIO 设备模型的理解更具体了

之前我知道 VirtIO 是虚拟化设备标准，但比较抽象。通过这次实验，我更具体地理解了：

1. MMIO 地址空间中的设备头部如何被访问
2. 驱动初始化如何通过 transport 完成
3. framebuffer 为什么需要 DMA 连续内存
4. 为什么驱动初始化成功并不等于图像一定已经显示，还需要 `flush()`

这些理解比只看教程文字更扎实。

#### 9.1.3 对 framebuffer 图形输出的理解更具体了

这次实验让我第一次在操作系统实验环境里亲手打通了：

- 图形数据表示
- 多边形光栅化
- 像素写入
- 屏幕刷新

虽然只是静态图像，但它为后续做 `ch2-moving-tangram`、`snake`、`tetris` 之类更复杂的图形实验打下了基础。

### 9.2 能力方面的提升

#### 9.2.1 工程拆解能力提升

原始要求一句话写的是“显示七巧板图案”，看起来很简单。但真正落地时需要拆解成：

1. 运行环境修改
2. 驱动引入
3. 内存支持
4. 图形数据设计
5. 像素绘制
6. 人工与自动验证

这次实验让我更意识到，很多操作系统任务看起来简单，真正实现时必须拆成多个可以独立验证的小问题。

#### 9.2.2 调试能力提升

这次虽然没有碰到特别深的 trap 问题，但我切实练习了：

- 根据编译报错快速回溯到缺失的系统能力
- 通过串口日志判断驱动初始化进行到了哪一步
- 用人工验证和脚本验证双重确认结果

这比单纯“跑通一次就结束”更接近真实工程开发。

#### 9.2.3 与 AI 协作的能力提升

以前我更容易把 AI 当成“问答工具”，这次更像是在练习“如何管理一个协作式开发助手”。

我学到的一个重要方法是：

1. 先让 AI 看代码库
2. 再让 AI 给实现路径
3. 每完成一块就验证
4. 发现问题后要求 AI 聚焦解决当前阻塞点

这种协作方式比一次性让 AI 大包大揽更稳。

### 9.3 本实验中能力是否有“下降”

如果如实评价，我认为也有一个潜在风险：

> 如果对 AI 生成的方案和代码不做主动核对，自己容易在“局部实现细节”上变得依赖。

例如本实验中，如果我完全不关注：

- 为什么 `virtio-drivers` 需要分配器
- 为什么需要 DMA
- 为什么要改 QEMU runner

那我虽然也能得到一个“能跑的结果”，但对操作系统机制的理解会明显下降。

所以我的结论是：

- AI 本身不会自动提升能力
- 只有在“先理解问题，再利用 AI 加速分析与实现”的前提下，能力才会提升

## 10. 本实验的不足与后续改进方向

虽然本次实验已经完成核心目标，但我认为仍有几个可以继续改进的地方。

### 10.1 图形数据表示还可以进一步贴近“像素数组直接渲染”

本次使用的是“顶点数组 + 软件光栅化”方案。它有教学优势，但如果严格按最字面的要求理解，后续还可以增加一个版本：

1. 离线生成完整像素数组
2. 运行时直接拷贝到 framebuffer

这样会更接近“像素数据直接渲染”的表述。

### 10.2 目前仍然是静态图案，没有动态过程

当前版本只完成了静态显示。后续如果做 `ch2-moving-tangram`，可以继续扩展为：

- 分阶段显示每一块
- 做简单动画
- 体现多程序批处理特性

### 10.3 目前的内存支持是“最小可用”，不是通用实现

本次为了保持 `ch1` 简洁，只实现了够用的静态 DMA 和堆分配。后续如果实验规模变大，最好引入更规范的内存管理框架。
