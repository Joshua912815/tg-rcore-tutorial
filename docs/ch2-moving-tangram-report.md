# `ch2-moving-tangram` 游戏实验独立总结报告

## 1. 实验背景与任务理解

本实验对应 `tg-rcore-tutorial` 根目录 `README.md` 中给出的 `ch2-moving-tangram` 要求：

> 在 ch2 基础上扩展内核功能，动态分步显示七巧板“OS”图案，即通过多程序批处理方式，每个程序渲染一块，逐块渲染七巧板“OS”的 n 个组成部分，实现动态拼接的视觉效果。

我对这个要求的理解是：

1. 这不是把 `ch1-tangram` 机械复制到 `ch2`，而是要体现 `ch2` 的核心教学主题，也就是“多程序批处理系统”。
2. `ch2-moving-tangram` 的重点不是单纯显示最终图案，而是让多个用户程序按批处理顺序依次运行，每个程序负责渲染一块七巧板，最终在屏幕上逐步拼出完整的 “OS” 图案。
3. 与 `ch1` 相比，本实验必须同时打通两条链路：
   - 一条是内核侧的 VirtIO-GPU + framebuffer 图形显示链路；
   - 另一条是 `ch2` 的批处理执行链路，即多个用户程序依次装载、执行、退出。
4. 由于 `ch2` 仍然是一个较简化的教学内核，没有后面章节那样完整的进程、文件系统和图形用户库，因此实现仍然要遵循“最小但完整”的原则。

因此，我给自己设定的实验目标不是“最终能看到一张图就行”，而是：

> 在 `ch2` 的批处理系统框架下，让多个用户程序通过最小图形 syscall 逐块渲染 Tangram 图案，真实体现 `ch2` 的多程序顺序执行能力。

## 2. 实验目标

本次 `ch2-moving-tangram` 独立实验的具体目标如下：

1. 从当前工作分支切出独立分支 `ch2-moving-tangram`，避免影响其他实验。
2. 在 `tg-rcore-tutorial-ch2` 中引入 VirtIO-GPU 与 framebuffer 支持。
3. 保留 `ch2` 的批处理系统主循环，让多个用户程序按顺序装载和执行。
4. 设计一个最小自定义 syscall，使用户程序能够请求“绘制某一块 Tangram”。
5. 在 `tg-rcore-tutorial-user` 中新增一组 `ch2_tangram_*` 用户程序，每个程序负责绘制一块七巧板。
6. 让 QEMU 以图形窗口方式运行，并能观察到“逐块拼接”的动态效果。
7. 形成一份独立实验报告，说明实现内容、AI 协作过程、bug 与修复过程，以及学习效果评估。

## 4. 我实际完成了哪些工作

### 4.1 扩展了 `ch2` 的运行方式

原始 `ch2` 的 `.cargo/config.toml` 仍然使用 `-nographic`，这会导致：

1. QEMU 没有图形窗口；
2. framebuffer 渲染结果无法直接观察；
3. 即使 GPU 初始化成功，也只能在终端看到串口日志。

因此我修改了 `tg-rcore-tutorial-ch2/.cargo/config.toml`，将 runner 改为：

- 保留串口输出到终端：`-serial mon:stdio`
- 保留 `-bios none`
- 显式挂载 `virtio-gpu-device,bus=virtio-mmio-bus.0`

这样做之后，`cargo run` 同时具备两种能力：

1. 在终端输出批处理日志和调试信息；
2. 在 QEMU 图形窗口中显示 framebuffer 图像。

### 4.2 将 `ch1` 的最小图形链路移植到了 `ch2`

我在 `tg-rcore-tutorial-ch2/Cargo.toml` 中新增：

```toml
virtio-drivers = "0.1.0"
```

然后在 `tg-rcore-tutorial-ch2/src/main.rs` 中补充了以下能力：

1. VirtIO-GPU 的 MMIO 初始化；
2. 最小 DMA Arena；
3. 最小 BumpAllocator；
4. framebuffer 建立与刷新；
5. 图形状态在整个 `ch2` 生命周期中的保存。

和 `ch1` 一样，这里没有引入高章节的大型内存管理框架，而是继续采用：

- 静态 DMA 内存池；
- 静态全局堆；
- 简化的 bump allocator；

这样做的原因是：

1. `ch2` 仍然处于教学早期阶段；
2. 当前实验只需要“够用的最小图形能力”；
3. 不应该为了一个游戏实验，把 `ch2` 过度改造成高章节结构。

### 4.3 新增了 `framebuffer` 与 `tangram` 图形模块

我在 `tg-rcore-tutorial-ch2/src/` 下新增了：

- `framebuffer.rs`
- `tangram.rs`

其中：

`framebuffer.rs` 负责：

1. 像素写入；
2. 清屏；
3. 三角形填充；
4. 凸多边形填充。

`tangram.rs` 负责：

1. 定义七巧板 “OS” 图案的几何数据；
2. 维护 13 个图形块的颜色和顶点；
3. 提供 `piece_count()`、`clear_scene()`、`draw_piece()` 等接口；
4. 完成逻辑坐标到当前分辨率的缩放和居中变换。

这里仍然沿用了 `ch1-tangram` 的“多边形数组 + 软件光栅化”方案，而没有直接使用完整像素贴图。这样做的优点是：

1. 数据更简洁；
2. 图形块更适合逐块分阶段渲染；
3. 更符合七巧板“由几何块拼接而成”的结构特征。

### 4.4 在 `ch2` 中设计了一个最小自定义图形 syscall

为了体现“每个用户程序渲染一块”的批处理思路，我没有让用户程序直接操作 GPU，而是在 `ch2` 内核里设计了一个最小自定义 syscall：

- syscall 编号：`0x1000`
- 语义：绘制编号为 `piece_id` 的一块 Tangram

这一设计的核心考虑是：

1. `ch2` 只有 `write` 和 `exit` 这样的基础 syscall，不适合直接复用复杂图形接口；
2. 用户态程序只需要表达“我要绘制第几块”，不应该承担 GPU 细节；
3. 内核统一维护 framebuffer 状态，更容易实现“已绘制块不重复绘制”的逻辑。

在实现上，我在 `main.rs` 中增加了：

1. `SYSCALL_DRAW_TANGRAM_PIECE` 常量；
2. `GameDisplay` 结构，维护 GPU、framebuffer 和已绘制位图；
3. `draw_tangram_piece(piece_id)`；
4. 在 `handle_syscall()` 中对 `0x1000` 的专门分发。

### 4.5 让多个用户程序真正体现“批处理逐块拼图”

为了匹配 `README.md` 中“每个程序渲染一块”的描述，我没有只写一个用户程序，而是在 `tg-rcore-tutorial-user/src/bin/` 中新增了 13 个程序，例如：

- `ch2_tangram_00_o_red.rs`
- `ch2_tangram_01_o_yellow.rs`
- `...`
- `ch2_tangram_12_s_blue_bottom.rs`

这些程序都通过 `user_lib::run_tangram_piece_app(piece_id, label)` 执行：

1. 向串口打印当前要绘制的块；
2. 调用自定义 syscall 请求内核绘制；
3. 正常返回 `0` 退出。

我还修改了 `tg-rcore-tutorial-user/cases.toml` 的 `ch2` 部分，使 `ch2` 的用户程序列表变成这 13 个 Tangram 子程序。

这意味着 `ch2` 内核启动后，批处理主循环会真正按顺序做下面这件事：

1. 加载一个用户程序；
2. 运行它；
3. 这个程序请求绘制一块；
4. 程序退出；
5. 加载下一个用户程序；
6. 重复直到 13 块全部绘制完成。

这正是 `ch2-moving-tangram` 最核心的教学价值。

### 4.6 修复了 `ch2` 运行链路中的工具与兼容性问题

为了让实验不只是“代码理论上能写”，而是真能在本机跑起来，我还做了几类运行链路修复。

#### 4.6.1 让 `build.rs` 优先使用仓库内的本地 `tg-rcore-tutorial-user`

原始 `ch2` 的 `build.rs` 默认会尝试 `cargo clone`，这在本地环境中可能失败。

因此我在 `tg-rcore-tutorial-ch2/.cargo/config.toml` 中增加了：

```toml
TG_USER_DIR = "../tg-rcore-tutorial-user"
```

这样 `ch2` 会直接使用仓库里已有的本地用户态 crate，而不是额外下载。

#### 4.6.2 让 `build.rs` 支持回退查找 `objcopy`

原始 `build.rs` 只尝试调用 `rust-objcopy`。但本机最开始没有安装 `cargo-binutils`，因此用户程序打包阶段失败。

为此我修改了 `tg-rcore-tutorial-ch2/build.rs`，增加以下策略：

1. 优先使用 `RUST_OBJCOPY` 环境变量；
2. 再尝试 `rust-objcopy`；
3. 最后回退到 Rust toolchain 自带的 `llvm-objcopy`。

这样在安装 `llvm-tools-preview` 后，整个构建链路就可以正常工作。

#### 4.6.3 修复了 Rust 2024 下 `tg-rcore-tutorial-syscall` 的 `asm!` 兼容问题

在真正编译 `ch2` 用户程序时，我遇到的一个阻塞点不是 `moving-tangram` 本身，而是：

- `tg-rcore-tutorial-syscall/src/user.rs`

在 Rust 2024 下，`unsafe fn` 内部的 `asm!` 需要显式 `unsafe {}` 包裹，否则由于 `#![deny(warnings)]` 会直接编译失败。

我因此补上了这几处 `unsafe { asm!(...) }`，保证用户态 syscall 封装能正常构建。

本实验不是停留在 `cargo check` 层面，而是已经真正运行成功。

实际运行流程如下：

3. 终端输出 GPU 初始化日志，例如：

4. 图形窗口中可以观察到七巧板 “OS” 图案逐块拼接完成；
5. 输入 `q` 后正常退出。

## 5. 关键实现思路

### 5.1 为什么 `ch2` 适合做 `moving-tangram`

相比 `ch1` 的静态图像显示，`ch2` 的核心主题是批处理系统，因此它非常适合做“分步拼图”而不是复杂交互游戏。

原因如下：

1. `ch2` 已经具备“多个用户程序顺序运行”的能力；
2. 但还没有时钟驱动、多道程序调度、输入系统等更复杂机制；
3. 如果在 `ch2` 直接做 `snake` 或 `tetris`，会引入大量与本章主题无关的机制；
4. `moving-tangram` 正好只需要：
   - 多个用户程序；
   - 基础 syscall；
   - framebuffer 渲染；
   - 顺序执行产生的动态视觉效果。

因此，它是最符合 `ch2` 教学定位的游戏实验。

### 5.2 为什么采用“内核统一绘图 + 用户程序发请求”的设计

我没有让每个用户程序自己维护图形设备状态，而是采用：

1. 内核统一持有 GPU 与 framebuffer；
2. 用户程序只通过 syscall 传递 `piece_id`；
3. 内核根据 `piece_id` 绘制对应图形块。

这样设计的优点是：

1. 代码结构清晰；
2. 图形状态不会因为用户程序切换而丢失；
3. 每个用户程序非常小，能更纯粹地体现“一个程序完成一块任务”的批处理思想；
4. 更符合教学实验中“用户态提出请求，内核执行特权操作”的分层思想。

### 5.3 为什么仍然采用几何顶点表示图形

和 `ch1-tangram` 一样，我继续使用顶点数组而不是整张像素贴图，原因是：

1. 七巧板天然是几何图形；
2. `moving-tangram` 要按块逐个绘制，几何块表示更直观；
3. 代码更短，可读性更好；
4. 更方便后续调整顺序、颜色和块编号。

这样做的目的，是避免把 `ch2` 做成“另一个静态 `ch1-tangram`”，而忽略 `ch2` 批处理系统的本质。

#### 第二阶段：让 AI 在剩余候选游戏里做难度判断

在真正开始做之前，我先让 AI 基于 `README.md` 的描述，判断除 `ch1-tangram` 与 `ch8-doom` 之外，哪个额外游戏最容易实现。

AI 最终选择了：

- `ch2-moving-tangram`

给出的主要理由是：

1. 可以大量复用 `ch1-tangram` 的图形数据和 framebuffer 绘制逻辑；
2. 新增点主要集中在 `ch2` 的批处理顺序执行；
3. 不需要输入系统、碰撞检测、计分、文件系统存档、信号或线程同步。

这个判断对我帮助很大，因为它帮我把第三个游戏实验选成了“最小增量、最大复用”的路线。

#### 第三阶段：先看 `ch1-tangram`，再移植到 `ch2`

我让 AI 先读取：

1. `ch1-tangram` 分支中的 `main.rs`；
2. `framebuffer.rs`；
3. `tangram.rs`；
4. 当前 `ch2` 的 `main.rs` 与 `build.rs`。

这样做之后，AI 很快确定了一条合理路径：

1. 图形渲染模块直接从 `ch1` 迁移；
2. `ch2` 保留原本的批处理主循环；
3. 通过一个最小 syscall 将两个部分连接起来。

这个方案比“让每个用户程序都直接操作 GPU”要稳得多。

### 6.2 AI 帮助我定位和解决的问题

#### 问题一：创建分支时的权限问题

最开始在仓库里创建分支时，Git 因为 `.git` 写入权限受限而失败。

AI 并没有停下来等我手工处理，而是识别出这是权限层问题，随后通过授权流程成功创建：

- `ch2-moving-tangram`

#### 问题二：`ch2` 真正跑起来不仅要改代码，还要补工具链

AI 在推进过程中没有停留在“代码大概写完了”，而是继续检查：

1. 是否安装了 `riscv64gc-unknown-none-elf`；
2. 是否安装了 `llvm-tools-preview`；
3. 是否存在 `rust-objcopy` 或 `llvm-objcopy`；
4. QEMU runner 是否真的会打开图形窗口。

这一步很重要，因为如果只写代码、不管工具链，实验最终仍然无法演示。

#### 问题三：GPU 设备总线挂载错误

第一次真正运行 QEMU 时，内核 panic：

```text
failed to create VirtIO MMIO transport: ZeroDeviceId
```

AI 很快判断出根因不是代码渲染逻辑，而是 QEMU runner 里把 GPU 设备挂到了错误的总线上：

- 错误：`virtio-mmio-bus.1`
- 正确：`virtio-mmio-bus.0`

修改后，GPU 初始化立即成功。

#### 问题四：黑条与颜色错乱

这是本次实验中最关键、也最值得写进报告的 bug。

现象是：

1. 图像主体大部分看起来基本正确；
2. 屏幕中间出现大块黑条；
3. 黑条上边缘有彩色噪点和颜色错乱；
4. 下方图案像被“撕裂”了一样。

AI 对这个问题的判断不是“绘制算法错了”，而是：

> 更像是 framebuffer 或 DMA 相关内存被其他数据覆盖了。

随后 AI 继续回溯地址布局，发现：

1. `ch2` 中新增了较大的静态 DMA 和 heap：
   - `DMA_ARENA_SIZE = 16 MiB`
   - `HEAP_SIZE = 1 MiB`
2. 而 `ch2` 的用户程序原本仍然装载到：
   - `0x8040_0000`

这说明用户程序加载地址和新加入的图形相关静态区发生了重叠或紧邻覆盖，用户程序被批处理装载时破坏了 framebuffer/DMA 所在内存。

AI 给出的修复方案是：

1. 将 `tg-rcore-tutorial-user/cases.toml` 中 `ch2` 的 `base` 从 `0x8040_0000` 提高到 `0x8200_0000`；
2. 重新构建并运行；
3. 检查日志中用户程序装载地址是否变成新的高地址。

修复后，日志显示：

```text
[ INFO] load app0 to 0x82000000
```

同时图像显示恢复正常，黑条与花屏消失。

### 6.3 与 AI 协作中的一个重要体会

这次我最大的体会是：

> 做操作系统图形实验时，AI 最有价值的地方不是“写多边形填充代码”，而是帮助我把运行异常映射回系统层的根因。

例如这次黑条问题，如果只盯着图像现象，很容易怀疑：

1. 填充算法错了；
2. 缩放公式错了；
3. BGRA/RGBA 通道顺序错了。

但 AI 帮我更快地跳到“内存被覆盖”这个更接近内核真实问题的层面，这一点非常有帮助。

## 7. 实际遇到的问题、Bug 与解决过程

### 7.1 QEMU 初次启动时找不到 GPU 设备

#### 现象

第一次启动时，终端报错：

```text
failed to create VirtIO MMIO transport: ZeroDeviceId
```

#### 分析

这说明内核访问的 MMIO 地址 `0x1000_1000` 上没有对应的 VirtIO-GPU 设备。问题不在渲染代码，而在 QEMU runner 的设备挂载位置。

#### 解决

将 `tg-rcore-tutorial-ch2/.cargo/config.toml` 中的 GPU 设备挂载位置改为：

```text
virtio-gpu-device,bus=virtio-mmio-bus.0
```

修改后 GPU 初始化成功。

### 7.2 黑条、彩色噪点和图像撕裂问题

#### 现象

在图像大部分已经能显示出来之后，屏幕中间出现了明显黑条，并伴随：

1. 黑条上缘彩色噪点；
2. 黑条上下图像错位；
3. 图案局部显示正常，但整体被一块大黑带截断。

#### 初始判断

从现象看，这不像纯粹的几何绘制错误，更像是 framebuffer 对应的内存被其他数据覆盖。

#### 根因分析

本实验在 `ch2` 中新增了较大的静态图形内存区：

1. 16 MiB DMA Arena；
2. 1 MiB Kernel Heap。

而 `ch2` 的用户程序原始装载地址仍然是：

```text
0x8040_0000
```

由于 `ch2` 会把所有用户程序反复装载到这一地址，当用户程序镜像与图形相关静态区地址发生重叠时，就会破坏 framebuffer/DMA 内容，最终表现为黑条、花屏和撕裂。

#### 修复方法

将 `tg-rcore-tutorial-user/cases.toml` 中 `ch2` 的装载基址改为：

```text
0x8200_0000
```

#### 修复结果

修复后：

1. 日志显示用户程序已从更高地址装载；
2. 图形窗口恢复正常；
3. 黑条和颜色错乱问题消失。

#### 这一 bug 的教学意义

这个问题非常值得写进报告，因为它体现了：

1. 图形问题未必是图形算法问题；
2. 在操作系统实验中，很多“显示异常”的根因其实来自地址布局和内存覆盖；
3. 图像异常可以反向帮助定位内存管理问题。

### 7.3 `build.rs` 依赖 `cargo clone` / `rust-objcopy` 导致无法完整构建

#### 现象

最开始完整构建时，`ch2` 会在用户程序构建和打包阶段失败。

#### 分析

原因有两个：

1. 默认会尝试 `cargo clone` 获取用户态 crate；
2. 默认只尝试 `rust-objcopy`，而本机未安装 `cargo-binutils`。

#### 解决

1. 在 `.cargo/config.toml` 中显式设置 `TG_USER_DIR` 指向本地 `tg-rcore-tutorial-user`；
2. 修改 `build.rs`，支持从 toolchain 中查找 `llvm-objcopy`；
3. 安装 `llvm-tools-preview`。

### 7.4 Rust 2024 下 syscall 封装编译失败

#### 现象

完整构建用户程序时，`tg-rcore-tutorial-syscall/src/user.rs` 中 `asm!` 相关代码在 Rust 2024 下直接报错。

#### 分析

由于该 crate 开启了 `#![deny(warnings)]`，`unsafe fn` 体内未显式包裹 `unsafe { asm!(...) }` 会被当成错误。

#### 解决

为这几处 `asm!` 调用补上显式 `unsafe {}` 包裹，使用户态 syscall 封装恢复可编译状态。

## 10. 本实验的不足与后续改进方向

虽然本次实验已经完成核心目标，但我认为仍有几个可以继续改进的地方。

### 10.1 当前动态效果仍然是“顺序逐块出现”，不是平滑动画

目前的动态效果主要来自：

1. 多个用户程序顺序执行；
2. 每次绘制一块后做一个短暂延迟。

这已经足以体现批处理系统，但如果后续想进一步增强表现力，可以考虑：

1. 对每块增加更细的中间帧；
2. 在内核或用户态增加更平滑的时间控制。

### 10.2 当前 syscall 是专门为本实验写的最小接口

`0x1000` 这个 syscall 足够完成实验，但它并不是一个通用图形接口。后续如果还要扩展更多 `ch2` 图形程序，可以进一步抽象为：

1. 清屏；
2. 绘制多边形；
3. 刷新；
4. 延迟。

### 10.3 当前地址布局是手动避让

本次黑条问题通过把用户程序装载地址从 `0x8040_0000` 提升到 `0x8200_0000` 解决了，但本质上仍是“手工布局”。如果后续实验更复杂，最好把内核静态区、DMA 区和用户程序装载区的边界整理得更明确。
