# Chapter 3 基础实验学习效果评估

## 1. 与 AI 合作的实现过程

本章采用了“先读题和代码，再让 AI 协助定位实现点与验证路径”的工作流。交互过程主要分成四段：

1. 先读 `exercise.md`，明确 `sys_trace(410)` 的三种行为，以及“查询 syscall 次数时，本次调用也要计入”的关键语义。
2. 再读 `src/main.rs` 和 `src/task.rs`，把 AI 的建议收敛到两个改动点：`Trace for SyscallContext` 的实现，以及系统调用分发入口的统一计数。
3. 在实现阶段，AI 主要负责帮助排查“统计状态应该放在哪里”这个设计问题，而不是直接代写整套代码。
4. 在验证阶段，AI 协助把验证分成 `cargo run --features exercise` 和 `./test.sh exercise` 两条路径，确保既能跑通，也能通过检查器。

## 2. 问题、Bug 与解决过程

本章最关键的问题不是 `trace` 读写本身，而是 syscall 计数的放置位置。

- 起初直觉上想把大数组直接放进 `TaskControlBlock`，按 syscall 编号下标统计。
- 实际尝试后，内核启动异常，表现为只打印 banner 或用户程序无法继续运行。
- 进一步分析后确认，`tcbs` 是放在 `rust_main` 局部作用域中的，这意味着 TCB 变大后会直接推高内核栈压力。
- 最终改成在 `task.rs` 中使用静态侧表保存“当前任务编号 + syscall 计数信息”，只在调度进入任务前设置当前任务编号，在 `handle_syscall()` 分发前统一记账。

这个修正过程让我真正意识到，内核里的“数据放在哪里”本身就是设计问题，不只是实现细节。

## 3. 验证过程

在 `rcore-docker` 容器中完成验证，核心验证点包括：

- `cargo run --features exercise` 输出中出现 `string from task trace test`
- `cargo run --features exercise` 输出中出现 `Test trace OK!`
- `./test.sh exercise` 通过检查器，结果为 `Test PASSED: 7/7`

这些验证不仅覆盖了 `trace` 的读写功能，也覆盖了 syscall 计数是否正确、是否把本次 `trace` 本身计入统计。

## 4. 学习效果评估

与做实验前相比，这一章最大的提升有三点：

- 能从“接口功能”上升到“内核状态布局”的层面思考问题。
- 能更自然地把 `handle_syscall()` 识别为统一统计入口，而不是在各 syscall 分支里零散补逻辑。
- 能把 AI 用在“读题、定位、归因、验证”四类高价值环节，而不是把它当成直接生成答案的工具。

也有一个需要警惕的点：如果过早依赖 AI 给出方案，而不先自己读题和看测试程序，很容易忽略题目中的语义细节，比如“本次查询调用也计入统计”。

## 5. 与校内教程实验的对比

和校内传统实验方式相比，这次 AI 协作方式有以下差异：

- 优点一：定位更快。以前常常需要自己在多个文件中来回翻找入口，现在可以先让 AI 帮忙缩小改动范围，再由自己做实现判断。
- 优点二：排查更聚焦。像本章这种“不是功能错，而是对象放错位置”的问题，AI 很适合做归因提示，能减少无效试错。
- 优点三：验证更完整。AI 会主动提醒同时保留运行验证和检查器验证，两条链路都过了以后，结果更可靠。

但 AI 协作并不意味着实验更轻松就一定更好。真正有效的前提是：自己先看题、先看代码、先理解测试目标，否则 AI 给出的建议也很容易被误用。

综合来看，这种方式比单纯照着校内教程逐步操作更高效，也更接近真实工程里的协作式开发过程，对理解内核代码组织和验证方法都有直接帮助。
