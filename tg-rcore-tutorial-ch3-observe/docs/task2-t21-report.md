# T2L21 设计总结报告

## 1. 设计思路与目标

本实验关注的不是“给 `ch3` 再加一个新功能”，而是把第三章里最关键的动态状态变成可以反复观察、反复验证的学习材料。具体目标是：

1. 在正常、异常、断点、崩溃四类场景下都能留下稳定日志。
2. 让日志不是零散信息，而是围绕任务级状态模型组织。
3. 保证实验不仅能在当前仓库里跑，还能打包成一个独立 crate 供他人复现。

我比较依赖“状态可见”的学习方式，所以这个实验的设计重点始终是：先把状态显式化，再把机制理解清楚。

## 2. 核心设计

### 2.1 任务级状态快照

在 `src/observe.rs` 中，为每个任务维护一份 `TaskObservation`，记录：

- 装载入口和初始栈
- 进入次数
- syscall 次数
- trace 请求次数
- yield 次数
- timer 中断次数
- breakpoint 次数
- exception 次数
- exit 次数
- 最近一次 syscall、`scause`、`sepc`、`stval`

### 2.2 delta 输出

仅靠完整快照不足以高效分析动态变化，所以额外维护“上一次快照”，在每次 dump 时打印 delta。这样能直接回答“刚才这一步到底改变了什么”。

### 2.3 指令长度感知的断点恢复

命中 `ebreak` 后，不固定 `sepc += 4`，而是先读取指令编码，判断是 16 位还是 32 位指令，再决定步长。这个改动直接修掉了最开始 breakpoint workload 无法正常结束的问题。

### 2.4 breadcrumb 崩溃路径

相对 baseline 侧重源码级 backtrace，本实验改成了更轻量的 breadcrumb 路径记录。它不能替代完整回溯，但更稳定、实现更简单，也更适合后续章节复用。

## 3. 与 AI 合作的实现过程

这次我把 AI 当成高频工程协作者，而不是答案生成器。协作过程主要是：

1. 我先给出题目边界、不能抄 baseline、要可复现、要能最终发布 crate 这几个硬约束。
2. AI 先梳理 `ch3` 的 trap 和任务路径，找出最有价值的观测点。
3. 代码完成后，AI 再负责补脚本、Docker 回归、GDB 入口、crate 元数据和文档。
4. 在实际从 crates.io 源包做干净复现时，首次进入 Docker 会先安装 Rust 工具链和组件，原先的回归脚本会被初始化时间拖慢。随后把 Docker 脚本改成显式准备工具链，再执行测试，保证首次复现也稳定通过。
5. 进一步验证后发现 crates.io 打包不会保留嵌套 user crate 目录，因此又把最小 user crate 改成 bundle 形式随包分发，并在 `build.rs` 中自动解包，避免对 `cargo-clone` 产生运行时依赖。
4. 遇到 breakpoint 恢复失败这类问题时，先看日志，再看指令编码，最终把恢复逻辑改对。

这种分工的好处是：我把更多注意力放在“实验应该证明什么”，而不是反复手搓脚本和目录整理。

## 4. 学习效果评估

### 4.1 能力提升

本实验让我对 `ch3` 的理解从“知道大概会发生 trap 和调度”提升到了“知道每个 trap 点具体改变了哪些状态”。尤其是：

- 对 `sepc / scause / stval` 的作用更熟悉
- 对 `ebreak` 恢复路径的细节更清楚
- 对实验交付的工程标准更明确

### 4.2 与现有实验教程的对比

和现有教程相比，这个版本的优势是：

1. 有统一的任务状态模型，而不是分散打印。
2. 有 delta 输出，日志分析成本更低。
3. 有脚本化回归和 Docker 复现，不依赖一次性手工操作。

定量上，本实验至少提供了三种可以直接复核的证据：

- breakpoint 成功恢复
- delta 日志成功输出
- crash 场景成功输出 breadcrumb

## 5. 结论

`T2L21` 最终形成的不是一个“只能在当前仓库里跑一次”的实验，而是一个可以独立分发、可复现、便于他人学习 `ch3` trap 与调度机制的 crate。
